# myportal 시스템 설계서

> 구현 기준 문서. 계획 수준의 상세는 `요건정의서.md`, 시각 원칙은 `디자인컨셉.md`/`DESIGN.md`를 따른다.

## 1. 시스템 개요

myportal은 사용자가 등록한 URL을 주기적으로 수집해 "지난번 방문 이후 새로 올라온 것"을 신문 데스크처럼 보여주는 서비스다. 단일 Next.js 애플리케이션 안에 프론트엔드와 Hono REST API가 함께 들어 있고, 데이터는 Supabase PostgreSQL의 `myportal` 스키마에 저장한다.

```text
Browser (React 19, App Router)
   │  @myportal/myportal-api-client (fetch, 표준 envelope)
   ▼
/api/[...path]  Next.js Route Handler (어댑터)
   │  /api 접두어 제거 후 전달
   ▼
Hono app (src/server/app.ts)
   │  request-id → CORS → 세션 게이트(/v1/*, auth·internal 면제)
   ▼
routes/*.routes.ts → features/* → features/*.sql.ts
   ▼
@ttoltori/database (pg Pool, transaction)
   ▼
PostgreSQL — schema myportal
```

외부 크롤링은 서버가 직접 수행한다: `scripts/crawl-tick.ts`(로컬) 또는 Vercel cron → `/v1/internal/crawl-tick`.

## 2. 패키지 구성

| 패키지 | 역할 | 위치 |
|---|---|---|
| `myportal-web` | Next.js 앱 전체 | 루트 |
| `@myportal/api-contracts` | 요청/응답 zod 스키마, 오류 코드, 공용 타입 | `packages/api-contracts` |
| `@myportal/myportal-api-client` | 엔드포인트별 클라이언트 함수 | `packages/myportal-api-client` |
| `@ttoltori/api-client-core` | `httpRequest`(envelope 파싱, 타임아웃, ApiError) | `packages/api-client-core` (로컬 복사본) |
| `@ttoltori/database` | `DatabaseClient`(query/transaction), Pool | `packages/database` (로컬 복사본) |
| `@ttoltori/hono-api-kit` | request-id 미들웨어, `AppError`, `success`/`error`/`paginated` 응답 envelope, `attachErrorHandling` | `packages/hono-api-kit` (로컬 복사본) |

`@ttoltori/*`의 canonical source는 `shared-packages` 워크스페이스다. 수정 시 원본을 바꾸고 로컬 복사본에 동기화한다.

`@ttoltori/hono-api-kit`은 myportal뿐 아니라 `worldvs-web` 등 동일 아키텍처(Next.js + Hono) 서비스에서 request-id 부여, 표준 응답 envelope(`{success, data|error, meta.requestId}`), notFound/onError 처리 wiring이 서비스마다 거의 동일하게 재구현되던 것을 공통화한 패키지다(CLAUDE.md §21 "세 번 이상 동일한 패턴이 나타날 때 공통화를 검토한다"). 서비스별 오류 코드 Union은 `AppError<TCode>`의 제네릭으로 좁혀 타입 안전성을 유지한다.

## 3. 인증/세션 설계

- **매직링크**: `magic_links`에 SHA-256 해시된 토큰(만료·1회용)을 저장. `confirm` 성공 시 `sessions` 행 생성 + `myportal_session` HttpOnly·SameSite=Lax 쿠키.
- **개발 모드**: `AUTH_DEV_MODE=true`이면 메일 발송 대신 응답 `devLink`로 링크를 돌려준다.
- **Supabase Auth**: `SUPABASE_URL`/`SUPABASE_SERVICE_ROLE_KEY`가 있으면 Supabase Admin API로 매직링크 발급·검증한다.
- **세션 게이트**: `app.ts`가 `/v1/*`에 대해 한 번만 `requireAuth`를 실행한다. `/v1/auth/`, `/v1/internal/`는 면제 — 서브 라우터별 `.use("/*")`는 병합 시 다른 라우트로 새어 나가므로 사용하지 않는다.
- **내부 인증**: `/v1/internal/*`는 공유 시크릿(SHA-256 해시 후 `timingSafeEqual`). 헤더 `x-internal-secret` 또는 `Authorization: Bearer`(Vercel cron은 GET+Bearer로 호출).
- `users`는 최초 로그인 시 자동 생성된다. `ALLOWED_EMAILS`가 설정되면 그 이메일만 허용.

## 4. 수집 아키텍처

```text
collectSource(sourceId)
  1. robotsAllowed 확인 (실패 시 status=fail 기록)
  2. 페이지 획득 — spec.render=true면 renderPage(헤드리스 브라우저),
     아니면 fetchPage(timeout 15s, 최대 4MB, 리다이렉트마다 SSRF 재검사)
  3. 전략별 추출
     - 목록 힌트 지정됨 → generateSpec(hint) (힌트 문자열을 포함한 영역 우선)
     - feed 감지(RSS/Atom) → parseFeed
     - JSON-LD ItemList → parseJsonLdList
     - 저장된 CrawlSpec → applySpec
     - 스펙 없음/실패 → generateSpec (DOM 휴리스틱)
  4. dedupeHash(sourceUrl+title)로 items 중복 제거 → 신규만 insert
  5. matchNewItemsForSubscribers — 구독 사용자 규칙 평가 → item_rule_matches
  6. clusterItems — titleKey로 묶기
  7. crawl_runs 기록 + sources 상태/주기 갱신
       - 신규>0 → interval=15분, status=ok
       - 신규=0 → interval×2 (최대 24h)
       - 추출 실패 연속 → 명세 자동 재생성(rebuild) 시도
```

**JS 렌더링 소스**: 초기 HTML에 목록이 없는 사이트(예: thinkcontest.com)는 `render.ts`의 헤드리스 브라우저로 렌더링한 DOM을 파싱한다. 분석 단계에서 정적 추출이 실패하거나 힌트 문자열을 못 찾으면 자동으로 렌더링 재시도하고, 성공하면 `spec.render=true`로 저장해 이후 수집·self-repair·rebuild-spec에서도 브라우저 경로를 유지한다. 실행 파일은 `CHROMIUM_PATH`로 지정하거나 로컬 Chrome/Chromium을 탐색하며, 서버리스 환경에서는 `@sparticuz/chromium`을 사용한다. 라이브러리는 `playwright-core`(런타임) + `playwright`(로컬 dev, 브라우저 다운로드용)다.

**기준선(baseline)**: 소스 최초 등록 시 `runBaseline`이 최근 ~20건을 `is_baseline=true`로 넣는다. 데스크 목록에는 다른 항목과 같이 보이되, 등록 사용자의 `item_states`에 읽음으로 마킹되어 신규 카운트·다이제스트 대상에서는 제외된다. 다른 사용자가 같은 소스를 나중에 구독하면 구독 시점의 기존 항목 전체가 그 사용자에게 읽음으로 마킹된다. 이후 수집부터 신규로 간주한다.

**명세 버전**: `crawl_specs`에 `spec jsonb`(itemSelector + 필드 셀렉터 맵 + 선택적 `hint`/`render`)를 버전별로 보관한다. `rebuild-spec`은 새 버전을 만들고 활성 버전을 교체한다. 수집 실패가 누적되면 collector가 자동으로 같은 경로를 탄다.

**목록 힌트**: 소스 등록 화면의 '목록 항목 힌트' 입력값은 `spec.hint`로 함께 저장된다. 자동 추정이 메뉴 등 다른 영역을 잡았을 때 사용자가 목록에 표시되는 항목 텍스트 일부를 지정하면, 그 문자열을 포함하는 영역을 기준으로 스펙을 생성한다. 힌트를 찾지 못하면 자동 추정으로 폴백한다. 저장된 힌트는 `rebuild-spec`과 collector의 self-repair 시에도 재사용된다.

**앵커 없는 목록**: `<a>` 없이 JS 클릭으로 상세를 여는 목록(`cursor:pointer`/`onclick`/`data-href` 등)도 항목으로 인식한다 — 버킷 생성은 앵커 필수 1차 패스가 실패한 뒤 2차 패스에서 허용한다. 제목은 `tit`/`title`/`subject` 계열 클래스나 h1-h6·strong에서 고르고, 링크는 ①항목의 `data-*`/onclick에 든 URL → ②`data-*` 키를 페이지의 쿼리스트링 URL 템플릿에 대입(예: `data-contest_pk` + `view.do?contest_pk=…`) 순으로 복원한다. 복원 실패 시 `link`는 null이다.

**링크 전용**: `fetch_strategy='link'`는 수집하지 않고 목록만 보관한다(robots 금지 사이트용).

**스케줄링**: `crawl-tick`은 `sources.next_crawl_at <= now()`인 소스를 최대 20개씩 처리한다. 로컬은 `pnpm crawl:watch`(60s 루프), 운영은 Vercel cron 30분 간격이다.

## 5. 데이터 모델 (핵심)

- `sources` — 정규화 URL(유니크), fetch_strategy, status, interval_minutes, next_crawl_at, fail 연속 카운터.
- `source_fields` — 소스별 필드 메타(key,label,type,role,visible,sort_order). role: title/link/published/deadline/summary/none.
- `crawl_specs` — 버전·생성방식(auto/rebuild/manual)·활성 플래그.
- `items` — 소스 공유 수집물(title,url,published_at,collected_at,excerpt,attrs jsonb,dedupe_hash,is_baseline,cluster_id).
- `item_states` — 사용자별 read/read_at/starred (공유 items와 분리).
- `subscriptions` — 사용자↔소스: display_name, category_id, paused, tagIds는 `subscription_tags`.
- `categories`(최대 3단계, user 소유), `tags`(user 소유), `keyword_rules`(keywords/exclude/scope/scope_id/action).
- `item_rule_matches` — 수집 시 판정된 규칙 매치(user,item → 최우선 1건).
- `crawl_runs`(수집 이력), `crawl_jobs`(수동 수집 큐), `digest_runs`(발송 이력), `manual_actions`(감사), `user_settings`(다이제스트/마지막 방문 시각).

## 6. 데스크 조합 (`/v1/desk`)

단일 요청으로 초기 화면에 필요한 전부를 내려준다: `now`, `lastVisitAt`, `categories`, `tags`, `subscriptions`, `keywordRules`, `items`(최신순, 기준선 포함, 읽음/별표/규칙매치/데드라인 조인), `clusters`, `meta{lastCollectAt, sourceCount, warnCount, userEmail}`.

- `deadlineAt`은 소스의 role=deadline 필드 값에서 파생한다 — `date_range` 타입이면 `{start,end}`의 `end`를 쓴다.
- 읽지 않은 항목 수·특수 뷰(키워드 알림/마감 임박/별표/미분류)는 서버에서 계산해 `meta`에 포함한다.
- `POST /v1/desk/heartbeat`가 `last_visit_at`을 갱신한다 — "지난번 이후 새 항목" 판정 기준.

## 7. 오류 처리 계약

- `AppError(code, message, status)` → 표준 오류 envelope. 코드는 `api-contracts`의 `errorCodes` 상수를 쓴다.
- `AppError`가 아닌 예외는 `INTERNAL_ERROR`로 치환하고 서버 로그에만 스택을 남긴다.
- Zod 검증 실패 → `VALIDATION_ERROR` + issues를 details에 포함.
- 외부 fetch 실패는 도메인 오류로 변환한다(`URL_UNREACHABLE`, `RATE_LIMITED`, `ROBOTS_DISALLOWED`, `EXTRACTION_FAILED`).

## 8. 프론트엔드 구조

- 프로토타입 `assets/tokens.css`의 CSS 변수를 `globals.css`에 그대로 이식해 신문/전보 디자인을 유지한다(1px 룰, 이중선, 라운드·그림자·그래디언트 금지).
- `masthead.tsx` — 사이트명/네비/테마 토글(localStorage `myportal-theme`, data-theme 속성).
- `shell.ts` — `showToast`, 실행취소 띠, 시간 포맷 유틸.
- `desk/desk-client.tsx` — 3패널 데스크: 범위 트리(좌), 항목 목록(중), 상세/교정지(우). j/k 이동, m 읽음, s 별표, o 열기, Shift+A 전체 읽음, `?` 도움말. mute 항목은 건수만 표시, 클러스터는 대표 1건만 노출.
- `useResizable` — `--pane-N-width` CSS 변수를 갱신하는 스플리터. 패널 구성을 인자로 받아 categories/keywords/digest에서도 재사용한다(localStorage 키는 페이지별).
- 모든 데이터는 `lib/api.ts`의 `MyportalClient`로 가져오고 401이면 `/login`으로 보낸다.

## 9. 보안 설계

- **SSRF**: `assertPublicUrl`이 사설/루프백/링크로컬/멀티캐스트 IP, `.local`/`.internal` 호스트, 인증정보 포함 URL을 차단한다. 리다이렉트 시에도 매 홉 재검사한다.
- **robots**: 도메인별 robots.txt를 파싱·캐시하고 수집 전에 검사한다. 금지 시 link-only로만 등록 가능.
- **SQL**: 모든 외부 값은 파라미터 바인딩. 동적 컬럼/테이블은 허용 목록만.
- **입력**: 경계의 모든 입력(URL, path, query, body, header, env, 외부 응답)은 zod로 검증한다.
- **비밀**: 시크릿 비교는 해시 후 `timingSafeEqual`. 세션·매직링크 토큰은 해시로만 저장.
- **출력**: 에러 envelope에 SQL/스택/프로바이더 원문을 넣지 않는다. 다이제스트 HTML은 이스케이프한다.

## 10. 운영 고려사항

- **마이그레이션**: `database/migrations/myportal/`에 순번 SQL을 추가한다. `schema_migrations`가 적용 여부를 기록해 재실행을 막는다. 적용된 파일은 불변.
- **수집 부하**: due 배치 20개, interval 지수 백오프로 유휴 소스 비용을 줄인다.
- **다이제스트**: `SMTP_URL` 없으면 `queued`로 기록만 한다. 발송 시각/요일은 사용자 타임존(기본 Asia/Seoul) 기준으로 digest-tick이 판정한다.
- **관측**: `crawl_runs`로 소스별 성공/실패·신규 건수를 추적하고 `manual_actions`에 사용자 수동 작업을 남긴다.
