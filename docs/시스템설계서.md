# myportal 시스템 설계서

> 구현 기준 문서. 계획 수준의 상세는 `요건정의서.md`, 시각 원칙은 `디자인컨셉.md`/`DESIGN.md`를 따른다.

## 1. 시스템 개요

myportal은 사용자가 등록한 URL을 주기적으로 수집해 "지난번 방문 이후 새로 올라온 것"을 신문 데스크처럼 보여주는 서비스다. 단일 Next.js 애플리케이션 안에 프론트엔드와 Hono REST API가 함께 들어 있고, 데이터는 Supabase PostgreSQL의 `myportal` 스키마에 저장한다.

```text
Browser (React 19, App Router)
   │  @myportal/myportal-api-client (fetch, 표준 envelope)
   ▼
/api/[...path]  Next.js Route Handler (어댑터)
   │  /api 접두어 제거 후 전달
   ▼
Hono app (src/server/app.ts)
   │  request-id → CORS → 세션 게이트(/v1/*, auth·internal 면제)
   ▼
routes/*.routes.ts → features/* → features/*.sql.ts
   ▼
@ttoltori/database (pg Pool, transaction)
   ▼
PostgreSQL — schema myportal
```

외부 크롤링은 서버가 직접 수행한다: `scripts/crawl-tick.ts`(로컬) 또는 Vercel cron → `/v1/internal/crawl-tick`.

## 2. 패키지 구성

| 패키지 | 역할 | 위치 |
|---|---|---|
| `myportal-web` | Next.js 앱 전체 | 루트 |
| `@myportal/api-contracts` | 요청/응답 zod 스키마, 오류 코드, 공용 타입 | `packages/api-contracts` |
| `@myportal/myportal-api-client` | 엔드포인트별 클라이언트 함수 | `packages/myportal-api-client` |
| `@ttoltori/api-client-core` | `httpRequest`(envelope 파싱, 타임아웃, ApiError) | `packages/api-client-core` (로컬 복사본) |
| `@ttoltori/database` | `DatabaseClient`(query/transaction), Pool | `packages/database` (로컬 복사본) |
| `@ttoltori/hono-api-kit` | request-id 미들웨어, `AppError`, `success`/`error`/`paginated` 응답 envelope, `attachErrorHandling` | `packages/hono-api-kit` (로컬 복사본) |

`@ttoltori/*`의 canonical source는 `shared-packages` 워크스페이스다. 수정 시 원본을 바꾸고 로컬 복사본에 동기화한다.

`@ttoltori/hono-api-kit`은 myportal뿐 아니라 `worldvs-web` 등 동일 아키텍처(Next.js + Hono) 서비스에서 request-id 부여, 표준 응답 envelope(`{success, data|error, meta.requestId}`), notFound/onError 처리 wiring이 서비스마다 거의 동일하게 재구현되던 것을 공통화한 패키지다(CLAUDE.md §21 "세 번 이상 동일한 패턴이 나타날 때 공통화를 검토한다"). 서비스별 오류 코드 Union은 `AppError<TCode>`의 제네릭으로 좁혀 타입 안전성을 유지한다.

## 3. 인증/세션 설계

- **매직링크**: `magic_links`에 SHA-256 해시된 토큰(만료·1회용)을 저장. `confirm` 성공 시 `sessions` 행 생성 + `myportal_session` HttpOnly·SameSite=Lax 쿠키.
- **개발 모드**: `AUTH_DEV_MODE=true`이면 메일 발송 대신 응답 `devLink`로 링크를 돌려준다.
- **Supabase Auth**: `SUPABASE_URL`/`SUPABASE_SERVICE_ROLE_KEY`가 있으면 Supabase Admin API로 매직링크 발급·검증한다.
- **세션 게이트**: `app.ts`가 `/v1/*`에 대해 한 번만 `requireAuth`를 실행한다. `/v1/auth/`, `/v1/internal/`는 면제 — 서브 라우터별 `.use("/*")`는 병합 시 다른 라우트로 새어 나가므로 사용하지 않는다.
- **내부 인증**: `/v1/internal/*`는 공유 시크릿(SHA-256 해시 후 `timingSafeEqual`). 헤더 `x-internal-secret` 또는 `Authorization: Bearer`(Vercel cron은 GET+Bearer로 호출).
- `users`는 최초 로그인 시 자동 생성된다. `ALLOWED_EMAILS`가 설정되면 그 이메일만 허용.

## 4. 수집·분석 아키텍처

수집(정기, LLM 없음)과 분석(등록·재분석·자가복구, LLM 선행)은 경로가 다르다. 둘을 잇는 것은 소스에 저장된 두 가지다: **추출 명세**(`crawl_specs.spec`, "가져온 것에서 무엇을 뽑는가")와 **수집 프로파일**(`sources.fetch_profile`, "어떻게 가져오는가").

### 4-1. 정기 수집 (`collectSource`) — LLM 호출 0회

```text
collectSource(sourceId)
  1. robotsAllowed 확인 (금지 시 status=pause)
  2. 활성 스펙 로드 + loadFetchProfile(source, spec)
       - sources.fetch_profile이 유효하면 그 값
       - 비어 있거나({}) 손상됐으면 spec.render로 mode를 유도 (손상일 때만 [collect] 로그)
  3. 페이지 획득 — 프로파일 mode가 결정한다
       - rendered: renderPage(url, { waitForSelector, settleMs, scrollToBottom })
                   (렌더링된 DOM에는 ETag/304 조건부 요청을 쓸 수 없다)
       - static / feed: fetchPage(url, ETag·Last-Modified 조건부 요청), 304면 unchanged
  4. 추출 — source.fetch_strategy가 결정한다 (렌더링 여부와 무관)
       - rss → parseFeed, structured → parseJsonLdList,
         html(기존 행의 'rendered' 포함) → applySpec, link → 수집 안 함
  5. dedupeHash(sourceUrl+title)로 items 중복 제거 → 신규만 insert
  6. matchNewItemsForSubscribers — 구독 사용자 규칙 평가 → item_rule_matches
  7. clusterItems — titleKey로 묶기
  8. crawl_runs 기록 + sources 상태/주기 갱신
       - 신규>0 → interval=15분, status=ok
       - 신규=0 → interval×2 (최대 24h)
  * 4에서 0건이고 fetch_strategy='html'이며 consecutive_failures >= 2이면 repairSpec(자가복구, 4-2)을 1회 시도한다.
```

정기 수집의 정상 경로(1~8)에는 LLM 호출이 없다. LLM이 돌 수 있는 곳은 `repairSpec` 하나뿐이고, 그것은 추출이 0건으로 끝난 뒤의 별도 분기다(요건정의서 CRAWL-03).

> **알려진 한계**: `consecutive_failures`는 수집이 **예외로 끝났을 때만** 증가한다(`catch` 블록). 사이트 개편으로 예외 없이 0건이 추출되는 경우는 카운터를 올리지 않으므로, 그 상태가 이어져도 위 자가복구 조건(`>= 2`)에 도달하지 못한다. 이 동작은 재설계 이전부터 있었고 이 작업에서 바꾸지 않았다. 0건이 계속되는 소스는 소스 상세에서 **다시 분석**을 직접 실행해야 한다.

`fetch_strategy`와 프로파일 `mode`는 **이중 저장이 아니다.** `fetch_strategy`는 추출 방식(`rss`/`structured`/`html`/`link`)만 담고, 렌더링 여부는 프로파일이 단독으로 담는다. 분석 결과가 예전에 `rendered`를 돌려주던 자리는 `html` + `profile.mode='rendered'`다. 이미 DB에 `fetch_strategy='rendered'`로 남은 행은 `extractRows`가 `html`과 같게 처리한다.

### 4-2. 소스 분석 파이프라인 (LLM 선행)

등록(`analyzeUrl`)·재분석(`reanalyzeSource`)·자가복구(`repairSpec`)가 같은 코어(`analyzeListing`/`runAnalysis`)를 쓴다. 알고리즘이 "어떤 DOM 패턴이 목록처럼 보이는가"를 맞히는 대신, **LLM이 페이지를 읽고 무엇이 목록 항목인지만 번호로 가리키면 코드가 그것을 셀렉터로 번역하고, LLM이 읽은 내용과 대조해 검증**한다. LLM은 CSS 셀렉터를 설계하지 않고, 반환값에 실행 코드가 없다(요건정의서 CRAWL-01).

```text
analyzeListing({ userId, url, hint, hintSetAt, sourceId, purpose, allowRepair })
  1. robots.txt 확인                         금지 → blocked (link-only)
  2. 정적 fetch                              접근 실패 → blocked (error)
  3. RSS/Atom 조기 종료                      URL 자체가 피드 / 페이지의 피드 링크 → 항목이 있으면 렌더링·LLM 없이 끝
  4. 렌더링  renderPage(url)                 → { html, finalUrl, timings }
                                             (실패해도 정적 HTML로 계속하고 단계에 warn)
  5. 페이지 개요  buildPageOutline(html)     → { text, refs[], document, truncated }
  6. runAnalysis
       LLM 경로  (hasLlm · 일별 한도 · 시간 예산 · 개요가 비어 있지 않음을 먼저 확인)
         readPage(개요, 힌트)                → pageKind, items[], listCandidates, suggested
         synthesizeSpec(개요, 해석)          → ref를 itemSelector + 필드 셀렉터로 번역
         verifySpec(html, 스펙, 해석)        → 추출 결과와 LLM 보고를 대조
         전체 폐기면 readPageRepair 1회 → 재합성·재검증
       폴백 경로 (LLM 불가·실패)
         generateSpec(렌더된 DOM) → 실패하면 parseJsonLdList → 둘 다 실패면 outcome=null (상세 페이지 경로)
  7. buildFetchProfile(정적 HTML, 렌더 HTML, 스펙, timings) → mode, waitForSelector, settleMs, ...
  → ListingAnalysis { steps, outcome, profile, suggested, listCandidates, pageKind, hintMatched, ... }
```

**JSON-LD는 조기 종료에서 빠져 있다.** JSON-LD가 있는 페이지도 렌더링·LLM 해석을 거치고, JSON-LD 파싱은 6단계의 폴백 경로(휴리스틱이 3행 미만일 때)에만 남는다. 사이트가 JSON-LD에 본문 목록이 아닌 빵부스러기·메뉴를 넣은 경우를 구분할 방법이 없기 때문이다.

#### 모듈 구조

```text
src/server/features/crawl/
├─ fetcher.ts, robots.ts, url.ts          전송·robots·SSRF 방어
├─ render.ts                              renderPage(url, { waitForSelector, settleMs, scrollToBottom })
│                                         → { html, finalUrl, timings: { readyMs, readyBy, grewByScroll } }
├─ extract.ts                             피드·JSON-LD·applySpec·stripNoise·parseDate. generateSpec은 폴백 전용
├─ dom-selector.ts                        셀렉터 생성 유틸 (relativeSelector, commonSelector 등)
├─ analyze.ts                             오케스트레이터 (analyzeListing, analyzeUrl). 1~5·7단계와 단계 로그
├─ analyze/
│  ├─ page-outline.ts                     번호 붙은 페이지 개요 + ref 맵
│  ├─ llm-read.ts                         LLM 호출(readPage, readPageRepair)·응답 스키마·힌트 매칭
│  ├─ selector-synthesis.ts               ref → itemSelector + 필드 셀렉터 (순수 함수)
│  ├─ verify.ts                           추출 결과 ↔ LLM 보고 대조, 임계치 판정
│  ├─ profile.ts                          수집 프로파일 측정·조립 (fetchProfileSchema, buildFetchProfile)
│  └─ run-analysis.ts                     6단계: LLM 경로·폴백·시간 예산·단계 로그
├─ collector.ts                           정기 수집, 자가복구(repairSpec), 소스 생성
├─ cluster.ts
└─ llm/
   ├─ llm-client.ts                       전송 계층 (chatJson: 스키마 검증 + 재시도, timeout)
   ├─ usage.ts, usage.sql.ts              일별 한도 판정·호출 이력(llm_calls)
   └─ html-digest.ts                      HTML 축약 유틸. 현재 이 파일을 쓰는 운영 코드는 없다(자체 테스트만 참조)
```

설계 초안에 있던 `llm/enrich.ts`(휴리스틱 결과에 LLM 필드 덧붙이기)와 `llm/field-inference.ts`(LLM에게 셀렉터 설계시키기)는 역할이 사라져 삭제했다. 폴백 경로는 LLM을 쓸 수 없는 상황이므로 LLM 필드 추론도 쓰지 않는다.

#### 단계별 책임

| 단계 | 모듈 | 하는 일 |
|---|---|---|
| 렌더링 | `render.ts` | `goto(domcontentloaded)` → `waitForSelector`가 있으면 DOM에 붙는 즉시 완료(`readyBy: "selector"`), 없으면 networkidle·DOM 안정화 폴링으로 판정하고 `readyMs`·`readyBy`를 측정한다. 분석 시점에는 `waitForSelector`를 모르므로 시간 기반 판정을 타고 그 시간을 **측정**하며, 수집 시점에는 프로파일 값으로 조기 종료한다. SPA hash 라우트(`#/…`)는 원본 URL의 것을 보존해 렌더링한다. |
| 개요 | `page-outline.ts` | `stripNoise` 적용 DOM에서 들여쓰기로 깊이를 보이는 텍스트 개요를 만든다. 의미 있는 텍스트 노드와 링크·이미지에 `[n]`을 붙이고(앵커는 `a→경로 "텍스트"`), 텍스트 노드는 120자, 개요 전체는 48KB로 절단한다(뒤에서 자름, `truncated`). 끝에 **원본 문서**의 앵커를 최대 40개 `- 라벨 → URL`로 덧붙인다(번호 없음, 상세 페이지에서 목록으로 가는 링크를 찾는 용도). |
| 해석 | `llm-read.ts` | 시스템 프롬프트 + 개요(+ 힌트 한 줄과 개요의 `◀단서` 표시)를 보내 `pageKind`(`list`/`detail`/`unknown`), `pageTitle`, `items`(최대 12건 × 필드 12개, 값은 `[n]` 번호와 그 텍스트), `listCandidates`(최대 5), `suggested`(표시 이름·카테고리 경로·태그)를 받는다. 응답은 Zod로 검증하고 개요에 없는 번호는 거부한다. `temperature` 0, 응답 토큰 상한 8,000, 시도 timeout 상한 40초. |
| 합성 | `selector-synthesis.ts` | ① ref 해소 — 번호가 가리키는 요소의 텍스트가 LLM이 적은 텍스트를 포함하지 않으면 값으로 문서를 재탐색한다(`remapped`). ② 항목 루트 — 첫 두 제목의 최초 분기 조상, 셋째로 교차 검증. ③ `itemSelector` — 모든 루트를 포함하는 공통 셀렉터를 만들고, 루트들의 **최저 공통 조상 밖**에서 초과 매칭되면 조상을 접두로 붙여 좁힌다(`narrowItemSelector`). ④ 필드 셀렉터 — 항목마다 뽑은 상대 셀렉터를 공통 접미로 일반화하고 모든 루트에서 실행해 검증한다. ⑤ `titleSelector`/`linkSelector`/`publishedSelector` 지정(`role: published` 필드는 버리지 않고 `publishedSelector`로 승격, 제목이 항목 자신이면 센티넬 `:self`). 합성 불가(제목 해소 2개 미만 / 항목 루트 불분기 / `itemSelector` 불가)면 null → 폴백. |
| 검증 | `verify.ts` | 합성한 스펙으로 `applySpec`을 실제 실행해 LLM 보고와 대조한다(아래 표). 필드 셀렉터 문법 오류는 그 필드만 실패로 처리한다. |
| 프로파일 | `profile.ts` | 같은 스펙을 **정적 HTML과 렌더 DOM 양쪽에 적용**해 비교해 `mode`를 정한다(추측하지 않는다). |

검증 임계치(`verify.ts`):

| 항목 | 기준 | 미달 시 |
|---|---|---|
| 추출 행 수 | ≥ 3 | 전체 폐기 → 보수 호출 |
| 추출 행 수 | ≥ min(보고 항목 수, 10) × 0.7 | 전체 폐기 → 보수 호출 |
| 행 수율 `rowYield` (= 추출 행 / `itemSelector` 매칭 수, 상한 100) | ≥ 0.6 | 전체 폐기 → 보수 호출 |
| 제목 일치율 (추출 제목이 LLM 보고 제목을 포함, 300자 절단 후 비교) | ≥ 0.8 | 전체 폐기 → 보수 호출 |
| 필드 채움률 | ≥ 0.3 | 그 필드만 폐기 (보수 없음) |
| 필드 값 일치율 (`href`/`src`/`datetime` 필드는 비교하지 않고 채움만 본다) | ≥ 0.5 | 그 필드만 폐기 (보수 없음) |

텍스트 비교는 단방향(추출값 ⊇ LLM 텍스트)이다. 양방향이면 한 칸 밀린 짧은 요소가 긴 텍스트에 포함되어 어긋난 셀렉터가 통과한다.

#### 핵심 불변식 두 가지

**(a) 개요의 ref 공간은 `applySpec`이 보는 DOM(= `stripNoise` 적용 후)과 동일해야 한다.** `applySpec`은 추출 전에 `stripNoise(document)`로 `nav`/`header`/`footer`/`aside`/노이즈 컨테이너를 제거한다. 개요를 원본 DOM에서 만들면 LLM이 가리킨 노드가 수집 시점에는 없어, **검증은 통과하는데 수집에서 엉뚱한 요소를 뽑거나**(`nth-child` 위치가 어긋남) 0건이 된다. 그래서 `buildPageOutline`은 `parseHTML` + `stripNoise`만 적용한 문서를 쓰고 그 외의 변형을 가하지 않는다. 구현하면서 같은 종류의 어긋남이 둘 발견되었다.

- 설계 초안의 "개요에서 `svg` 추가 제거"는 삭제했다. `applySpec`은 `svg`를 지우지 않으므로 개요가 지우면 형제 구성이 달라진다.
- linkedom의 `document.body` getter는 `<head>`가 없으면 `<head></head>`를 문서에 삽입한다. 개요 문서만 `html`의 자식 구성이 달라지므로 `documentElement.querySelector("body")`를 쓴다.

`page-outline.test.ts`가 개요 문서와 `parseHTML`+`stripNoise` 문서의 `documentElement.outerHTML`이 완전히 같음을, 노이즈가 가득한 문서·`head`만 있는 문서·빈 문자열 등 여러 입력으로 단언한다. **개요를 만드는 코드에 DOM 변형을 추가하면 이 테스트가 깨져야 정상이다.**

**(b) `hintSetAt`은 힌트 문자열이 바뀔 때만 갱신된다.** 힌트는 목록 내용이 바뀌면 반드시 낡는데, 갱신 경로가 날짜를 리셋하면 낡음 경고(힌트 입력일·경과일)가 영구히 뜨지 않는다. 다음 세 경로가 모두 이 규칙을 지킨다.

| 경로 | 처리 |
|---|---|
| 재분석 (`reanalyzeSource`) | 힌트 생략 또는 저장값과 같은 값이면 저장된 `hintSetAt`을 `analyzeListing`에 넘겨 보존한다. `""`·다른 값이면 넘기지 않는다. |
| 적용 (`applySpecForSource` → `stampHint`) | 클라이언트 spec에 실려 온 `hint`/`hintSetAt`은 버리고 서버가 정한다. 생략 → 저장된 값 유지, `""` → 둘 다 삭제, 저장값과 같은 문자열 → 시각 보존(저장된 스펙에 시각이 없었다면 없는 채로), **다른 문자열 → 현재 시각**. |
| 자가복구 (`repairSpec`) | 저장 직전에 `hint`/`hintSetAt`을 이전 스펙 값으로 되돌린다. 힌트 없이 1회차에서 성공해도 사용자가 입력한 힌트와 시각을 지우지 않는다. |

시각을 새로 찍는 곳은 `stampHint`의 "다른 문자열" 분기 하나뿐이다(새 힌트가 처음 분석에 쓰일 때 `runAnalysis`가 "지금"을 찍는 것도 진짜 입력 시점이다).

#### `spec.render`와 `fetch_profile`은 상보 관계다 (중복이 아니다)

렌더링 필요 여부가 스펙(`spec.render`)과 프로파일(`sources.fetch_profile.mode`) 양쪽에 남는 것은 서로 다른 실패 경로를 덮는 이중 방어다. 분석은 프로파일이 `rendered`이면 스펙에도 `render=true`를 입힌다(`withRenderFlag`).

| 상황 | 렌더링을 유지하는 쪽 |
|---|---|
| 등록 시 클라이언트가 보낸 프로파일이 서버 재검증에 실패해 **프로파일 없이** 등록된 소스 | `spec.render` — `loadFetchProfile`이 `profileFromLegacySpec`으로 mode를 유도한다. 이 플래그가 없으면 렌더링 필요 소스가 정적 HTML로 0건을 받아 조용히 죽는다. |
| 자가복구가 **스펙을 새 버전으로 교체**해 `spec.render`가 사라진 소스 | 프로파일 — `repairSpec`은 `fetch_profile`을 건드리지 않는다. |
| 적용(`apply-spec`)의 검증용 재추출 | `spec.render` — `fetchAndExtract`가 이 플래그로 렌더링 여부를 정한다. |

둘 중 하나를 "중복"이라며 지우면 위 상황 중 하나에서 렌더링 소스가 조용히 0건이 된다.

#### 과포함의 책임 분담

`itemSelector`가 목록 밖의 반복 요소(사이드바, 메뉴)까지 잡는 과포함은 세 단계가 나눠 맡는다. LLM은 항목을 최대 12건만 보고하므로 "보고 수의 N배" 같은 수량 상한은 정상 목록(50건)을 거부해 쓰지 않는다.

| 단계 | 맡는 범위 | 못 잡는 것 |
|---|---|---|
| 합성 (`narrowItemSelector`) | 보고된 모든 항목 루트의 **최저 공통 조상 밖**의 초과 매칭을 조상 접두로 좁힌다. | 공통 조상 **안쪽**의 초과분(같은 컨테이너 안의 페이저·관련 링크 등) |
| 검증 (`rowYield` ≥ 0.6) | 셀렉터가 매칭했지만 행이 되지 못한(제목·앵커 없음) 요소가 40%를 넘으면 폐기한다. | **앵커가 있는 메뉴 항목** — `applySpec`은 앵커만 있으면 행으로 만들므로 수율이 1로 나온다. |
| 분석 단계 표시 + 미리보기 | `셀렉터 합성·검증` 단계에 `항목 N건, 제목 일치율 X%, 수율 Y`를 남긴다. 사용자가 이 지표와 추출 미리보기(최대 10행)를 함께 보고 판단한다. | 사람이 없는 자가복구 경로 |

수율만으로는 앵커가 있는 메뉴 항목을 못 잡는다는 점이 지표를 분석 단계에 표시하는 이유다.

#### 시간 예산

`route.ts`의 `maxDuration = 120`초 안에 분석이 끝나야 한다. 한도를 넘으면 플랫폼이 중간에 끊어 폴백도 못 타고 응답이 없는데, 이것이 가장 나쁜 실패다. LLM 앞단의 최악 소요는 고정할 수 없고(fetch 15초 + 브라우저 기동 + 렌더링 최대 약 51초) LLM 호출은 중간에 중단할 수 없으므로, **고정 마감 대신 호출 직전의 남은 시간으로 시도 timeout을 산출**한다(`run-analysis.ts`의 `attemptTimeoutMs`, 첫 호출과 보수 호출 모두).

```text
남은 예산    = 120초 − (지금 − 분석 시작) − 꼬리 여유 10초
시도 timeout = clamp(남은 예산 ÷ 스키마 시도 횟수 2, 하한 15초, 상한 40초)
(남은 예산 ÷ 2)가 하한 15초 미만이면 LLM을 호출하지 않고 폴백
```

호출의 최악 소요(시도 timeout × 2)가 남은 예산 이하이므로 합계가 구조적으로 한도 안에 들어가고, 꼬리 10초는 호출 뒤의 합성·검증·프로파일 계산과 응답 몫이다. 자가복구의 두 분석은 `collectSource`의 시작 시각을 하나의 `startedAt`으로 공유한다(각자 시계를 새로 시작하면 합계가 한도를 넘는다).

| 호출 시점 경과 | 시도 timeout |
|---|---|
| 5초 | 40초 (상한) |
| 60초 | 25초 |
| 80초 | 15초 (하한 경계) |
| 90초 | 호출 안 함, 폴백 |

`PLATFORM_MAX_DURATION_MS`(`run-analysis.ts`)는 `maxDuration`과 손으로 일치시킨 값이다. 어댑터 계층(`route.ts`)을 `src/server/`가 import하지 않기 때문이며, 한쪽을 바꾸면 다른 쪽도 바꾼다. `LLM_MAX_ATTEMPTS`(2)는 `llm-client.ts`의 스키마 시도 횟수와 같아야 한다.

#### 폴백 경로

LLM을 쓸 수 없거나(미설정, 일별 한도 초과, 호출 실패, 시간 예산 부족, 개요가 비어 있음) 합성·검증에 실패하면 휴리스틱을 **렌더된 DOM에** 적용한다: `generateSpec`(3행 이상이면 채택, `fieldSource="heuristic"`, 필드는 제목·링크·게시일만) → 실패하면 `parseJsonLdList`(3건 이상이면 `structured`) → 실패하면 `outcome=null`(상세 페이지 경로, 부모 후보는 URL 경로 자르기 + 링크 텍스트 패턴). 폴백은 반드시 분석 단계에 `warn`으로 남아 사용자가 필드가 비는 이유를 알 수 있다. 사유 문구는 고정값이며 프로바이더 원문 오류는 서버 로그에만 남는다(NFR-S5).

| 상황 | 단계 라벨 | 문구 |
|---|---|---|
| LLM 미설정 | AI 페이지 해석 | AI 분석이 설정되지 않았습니다 — 패턴 추정으로 진행 |
| 한도 초과 | AI 페이지 해석 | 일별 AI 분석 한도를 초과했습니다 — 패턴 추정으로 진행 |
| 호출 실패 | AI 페이지 해석 | AI 분석 호출에 실패했습니다 — 패턴 추정으로 진행 |
| 시간 부족 | AI 페이지 해석 / AI 재해석 | 분석 시간이 길어 AI 해석(재해석)을 건너뛰었습니다 — 패턴 추정으로 진행 |
| 빈 개요 | AI 페이지 해석 | 페이지에서 읽을 내용을 찾지 못했습니다 — 패턴 추정으로 진행 |
| `list`라 답하고 항목이 비어 있음 | AI 페이지 해석 | AI가 목록 페이지라고 답했지만 항목을 하나도 짚지 못했습니다 — 패턴 추정으로 진행 |
| 합성 실패 | 셀렉터 합성 | AI가 읽은 항목을 셀렉터로 옮길 수 없었습니다 — 패턴 추정으로 진행 |
| 검증 미달(보수 후) | 셀렉터 합성·검증 | 추출 결과가 AI가 읽은 내용과 달랐습니다 — 패턴 추정으로 진행 (항목 N건, 제목 일치율 X%, 수율 Y) |

`pageKind`가 `detail`/`unknown`이고 `items`가 비어 있으면 폴백하지 않는다 — 모델이 상세 페이지로 본 곳에서 패턴 추정이 메뉴를 목록으로 집는 것을 막기 위해 `outcome=null`로 상세 페이지 경로(부모 목록 후보 제시)를 탄다.

#### LLM 호출 지점과 비용

호출 지점은 `run-analysis.ts`의 두 곳(`readPage`, `readPageRepair`)뿐이고, 둘 다 성공·실패와 무관하게 `llm_calls`에 이력을 남긴다.

| 경로 | LLM 호출 | purpose / 한도 |
|---|---|---|
| 등록 분석 | 0~2회 (RSS 조기 종료·미설정·한도 초과·시간 부족·빈 개요면 0, 검증 통과면 1, 전체 폐기면 보수 +1) | `analyze-fields` / 사용자별 `LLM_DAILY_LIMIT` |
| 재분석 | 0~2회 (위와 같음) | `rebuild` / 사용자별 |
| 자가복구 1회 | 0~2회 — 힌트 없이 ≤1, 그것이 실패하고 저장된 힌트가 있으면 힌트로 +≤1. 두 호출 모두 보수 없음(`allowRepair: false`) | `self-repair` / 시스템 `LLM_DAILY_LIMIT_SYSTEM` |
| **정기 수집** | **0회** | — |

`chatJson` 안의 스키마 재시도(최대 2시도)는 이력상 호출 1건이다. 일별 한도는 `llm_calls`의 당일 **성공(`ok=true`) 건수**로 판정하고, 판정 쿼리가 실패하면 차단한다(fail-closed). 한도는 분석 시작 시 한 번만 확인하므로 보수 호출로 1회 넘을 수 있는 소프트 상한이다. 모델은 `LLM_MODEL`(기본 `gpt-4o-mini`) 하나이며 분석 전용 상위 모델 분리는 하지 않았다.

#### 수집 프로파일 (`profile.ts`)

```ts
fetchProfile = {
  mode: "feed" | "static" | "rendered",
  waitForSelector?: string,   // 로딩 완료 판정 셀렉터. 보통 itemSelector
  settleMs?: number,          // 시간 기반 대기 상한 (양수만 허용)
  scrollToBottom?: boolean,
  measuredReadyMs?: number,
  measuredReadyBy?: "selector" | "networkidle" | "stabilized" | "timeout",
  measuredAt: string,         // ISO 8601
}
```

- `mode`: 전략이 `rss`면 `feed`. 아니면 같은 스펙을 정적 HTML과 렌더 DOM에 적용해, 렌더 결과가 1건 이상이고 정적 결과가 렌더 결과의 80% 이상이면 `static`, 아니면 `rendered`. `structured` 전략은 `applySpec`이 아니라 `parseJsonLdList`로 센다(셀렉터가 없어 항상 0건이 되어 매번 `rendered`로 판정되는 것을 막는다).
- `settleMs = clamp(measuredReadyMs × 1.5, 1,500, 20,000)`. `readyBy`가 `timeout`이면 측정한 시간을 믿지 않고 상한 20,000을 쓴다. `waitForSelector`가 먼저 잡히면 `settleMs`는 쓰이지 않으므로 넉넉해도 비용이 없다.
- `waitForSelector`는 렌더 결과에서 1건 이상 뽑힌 `itemSelector`만 담는다(못 뽑은 셀렉터는 수집마다 대기 상한만큼 허비한다). 수집은 `state: "attached"`로 기다린다 — 접힌 영역·비활성 탭 안의 목록도 추출 기준(DOM 행)과 일치한다.
- `scrollToBottom`은 수집기가 따르지만, **현재 분석은 렌더링 시 스크롤을 켜지 않아 `grewByScroll`이 항상 false이므로 자동으로는 채워지지 않는다.**
- 저장 위치는 `sources.fetch_profile jsonb`(마이그레이션 `004_fetch_profile.sql`). `crawl_specs.spec`에 넣지 않는 이유는 수명이 다르기 때문이다 — 자가복구가 스펙을 교체해도 측정값은 보존되어야 한다. 빈 객체(`{}`)는 "아직 측정하지 않음"이며 읽는 쪽이 `spec.render`로 폴백한다. 백필 스크립트는 없다(전체 재분석은 LLM 비용이 소스 수만큼 들고, 수집은 기존 경로로 계속 동작한다).
- 클라이언트가 분석 결과에서 되돌려 보낸 프로파일(`profile`)은 신뢰하지 않고 서버가 `fetchProfileSchema`로 재검증한다. 검증에 실패하면 저장하지 않고 진행한다(원본 값을 로그에 싣지 않는다).

#### 힌트

힌트는 분석 시점에 목록에 보이던 제목의 일부 문자열이다. 목록 내용은 바뀌므로 **반드시 낡는다.** 그래서 보조 수단으로만 쓴다.

- **분석**: 힌트는 LLM 프롬프트의 한 줄과 개요의 `◀단서` 표시로만 작용한다. 목록 탐지를 힌트가 결정하지 않는다. 힌트가 개요에 없으면 단계에 `warn`("힌트 문자열이 현재 페이지에 없습니다 — 목록 내용이 바뀐 것 같습니다")을 남긴다. 힌트 매칭 판정은 LLM이 꺼져 있어도 로컬에서 항상 한다.
- **자가복구**: **힌트 없이 먼저** 시도하고, 실패했을 때만 저장된 힌트로 재시도한다(낡은 힌트가 복구를 영구히 막는 것을 방지).
- **재분석 화면**: 저장된 힌트를 입력일·경과일과 함께 보이고(`storedHint { value, setAt, matchesPage }`), **현재 페이지에서 매칭되지 않을 때만** 경고한다. 경과 일수만으로 경고하지 않는다(임의의 기준일을 만들지 않는다). 개요를 만들기 전에 끝난 분석(접근 실패·피드)은 판정 불가(`hintMatched=null`)라 경고하지 않는다. 힌트 요청은 생략(저장된 것 사용) / `""`(힌트 없이) / 값(덮어쓰기)을 구분하며, 적용(`apply-spec`)도 같은 세 가지 의사를 쓴다.
- **등록 화면**: 힌트 입력란에 "영구 설정이 아니다"라는 안내를 상시 표시한다. 힌트 미스로 끝난 분석은 응답 `pageText`에 렌더된 DOM의 텍스트 스냅샷(최대 400줄)을 담아 사용자가 새 힌트로 쓸 문자열을 직접 고르게 한다.

### 4-3. 기준선, 명세 버전, 재분석·재적용

**기준선(baseline)**: 소스 최초 등록 시 `runBaseline`이 최근 ~20건을 `is_baseline=true`로 넣는다. 데스크 목록에는 다른 항목과 같이 보이되, 등록 사용자의 `item_states`에 읽음으로 마킹되어 신규 카운트·다이제스트 대상에서는 제외된다. 다른 사용자가 같은 소스를 나중에 구독하면 구독 시점의 기존 항목 전체가 그 사용자에게 읽음으로 마킹된다. 이후 수집부터 신규로 간주한다.

**명세 버전**: `crawl_specs`에 `spec jsonb`(`itemSelector` + 필드 셀렉터 맵 + 선택적 `titleSelector`/`linkSelector`/`publishedSelector`/`hint`/`hintSetAt`/`render`/`fieldSource`)를 버전별로 보관한다. `apply-spec`이 새 버전을 만들고 활성 버전을 교체한다(생성방식 `manual`). 자가복구(collector의 `repairSpec`)도 같은 일을 한다(생성방식 `self-repair`). 스펙은 "무엇을 뽑는가"만 담고 "어떻게 가져오는가"(렌더링 여부·대기 시간)는 `sources.fetch_profile`이 담으므로, 스펙이 새 버전으로 교체되어도 프로파일은 바뀌지 않는다.

**재분석·재적용**: 등록된 소스의 스펙을 사용자가 확인하고 교체하는 경로다. LLM 선행 분석 이전에 등록된 소스나 사이트가 개편된 소스를 구제한다. 소스를 지우고 다시 등록하는 우회로는 막혀 있다 — 구독 해제는 `subscriptions` 행만 지우고, 같은 URL을 다시 넣으면 `analyzeUrl`이 중복으로 보고 분석을 건너뛰어 낡은 스펙을 그대로 물려받는다.

- **분석과 적용을 나눈다**: `POST /v1/sources/:id/reanalyze`는 **아무것도 저장하지 않고**(`llm_calls` 기록만 예외) 새 스펙·발견된 필드·추출 샘플·측정한 수집 프로파일(`preview.profile`)·저장된 힌트의 낡음 정보(`storedHint`)와 현재 저장된 필드(`currentFields`)를 돌려준다. 재분석 응답에는 `suggested`(표시 이름·카테고리·태그 제안)를 싣지 않는다 — 이미 등록된 소스는 이것들이 정해져 있다. 사용자가 소스 상세 화면의 인라인 패널에서 라벨·타입·역할·표시여부를 고친 뒤 `POST /v1/sources/:id/apply-spec`으로 확정한다. 미리보기 단계에 쓰기가 없으므로 '취소'는 되돌릴 것이 없다.
- **공통 코어**: `analyzeListing`(robots → fetch → 피드 조기 종료 → 렌더링 → 개요 → LLM 해석·합성·검증 → 프로파일, 4-2)을 등록(`analyzeUrl`)과 재분석(`reanalyzeSource`)이 공유한다. 코어는 robots 금지·fetch 실패를 예외로 던지지 않고 `blocked`로 돌려주며, 호출처가 각자의 응답 형태로 조립한다.
- **클라이언트 스펙을 신뢰하지 않는다**: `apply-spec`은 받은 스펙으로 페이지를 다시 받아 `extractRows`(수집 경로와 같은 함수)로 추출해 본다. 0건이면 `EXTRACTION_FAILED` 422로 거부하고 아무것도 저장하지 않는다.
- **백필**: 적용 직후 그 추출 결과로 기존 항목을 갱신한다. `dedupe_hash`가 `sha256(url + 제목)`이라 제목 추출이 달라지면 해시가 전부 바뀌므로, **`normalized_url`을 1차 매칭 키로 쓰고** URL을 복원하지 못한 행만 해시로 찾는다. 매칭된 항목은 `title`·`url`·`normalized_url`·`published_at`·`excerpt`·`attrs`와 **`dedupe_hash`까지 함께** 갱신한다 — 해시를 두면 다음 정기 수집이 새 제목으로 계산한 해시를 못 찾아 중복을 만든다. `attrs`는 교체가 아니라 병합해 새 분석에서 사라진 키의 값을 보존한다. 같은 URL의 기존 항목이 여럿이면 `collected_at`이 가장 오래된 1건만 갱신하고, 새 해시가 다른 항목의 것과 충돌하면 그 행을 건너뛴다(읽음·별표가 붙어 있어 삭제하지 않는다).
- **신규 삽입분**: 매칭되지 않은 행은 `is_baseline=false`로 넣고 **적용을 실행한 사용자의 `item_states`에만** 읽음 마킹한다. 내용은 과거의 것인데 `items`에만 없던 항목이라, 마킹하지 않으면 "지난 방문 이후 신규"가 수십 건 부풀어 데스크의 핵심 기능이 망가진다. 다른 구독자에게는 실제로 처음 보이는 항목이므로 그들의 상태는 건드리지 않는다.
- **보존되는 것**: 읽음·별표(`item_states`), 표시이름·카테고리·태그(`subscriptions`), 수집 이력(`crawl_runs`), 스펙 이력(`crawl_specs`). 일시정지(`status='pause'`)도 적용이 풀지 않는다.
- **공유 소스**: `crawl_specs`·`source_fields`는 소스 단위이므로 한 사용자의 적용이 다른 구독자의 데스크 라벨에도 반영된다. 최초 등록자가 모두를 위해 필드 메타를 정하는 기존 설계와 일관되며, `manual_actions`에 `apply-spec`으로 누가 언제 적용했는지 남긴다.
- **사라진 필드**: 사용자가 보낸 목록에 없는 기존 `source_fields` 행은 지우지 않는다. 기존 `items.attrs`에 그 키의 값이 남아 있어 데스크가 라벨을 필요로 한다. 패널이 "발견되지 않은 기존 필드 N개는 유지됩니다"로 알린다.
- **피드 전환**: 재분석이 RSS를 새로 발견하면 `fetch_strategy='rss'`와 함께 `sources.feed_url`도 갱신한다(`coalesce`). 수집 경로의 rss 분기는 `sources.feed_url`만 읽으므로 옮기지 않으면 그 소스가 영구히 0건을 반환한다.
- **프로파일 저장**: `apply-spec`이 받은 `profile`은 서버가 `fetchProfileSchema`로 재검증하고, 통과하면 **스펙 저장과 같은 트랜잭션**에서 `sources.fetch_profile`을 갱신한다. 검증에 실패하면 프로파일은 저장하지 않고(기존 프로파일 유지) 스펙 적용은 계속한다. 프로파일을 보내지 않으면 `fetch_profile`은 건드리지 않는다.
- **힌트**: 적용 요청의 `hint`는 재분석과 같은 세 가지 의사(생략 / `""` / 값)로 처리하며 `hintSetAt`은 문자열이 바뀔 때만 갱신된다(4-2 불변식 b).

**앵커 없는 목록** (폴백 휴리스틱 `generateSpec`): `<a>` 없이 JS 클릭으로 상세를 여는 목록(`cursor:pointer`/`onclick`/`data-href` 등)도 항목으로 인식한다 — 버킷 생성은 앵커 필수 1차 패스가 실패한 뒤 2차 패스에서 허용한다. 제목은 `tit`/`title`/`subject` 계열 클래스나 h1-h6·strong에서 고르고, 링크는 ①항목의 `data-*`/onclick에 든 URL → ②`data-*` 키를 페이지의 쿼리스트링 URL 템플릿에 대입(예: `data-contest_pk` + `view.do?contest_pk=…`) 순으로 복원한다. 복원 실패 시 `link`는 null이다.

**링크 전용**: `fetch_strategy='link'`는 수집하지 않고 목록만 보관한다(robots 금지 사이트용).

**스케줄링**: `crawl-tick`은 `sources.next_crawl_at <= now()`인 소스를 최대 20개씩 처리한다. 로컬은 `pnpm crawl:watch`(60s 루프), 운영은 Vercel cron 30분 간격이다.

## 5. 데이터 모델 (핵심)

- `sources` — 정규화 URL(유니크), fetch_strategy(추출 방식만), **fetch_profile jsonb**(수집 프로파일: 렌더링 여부 `mode`와 측정 대기값. `{}`는 미측정), status, interval_minutes, next_crawl_at, fail 연속 카운터.
- `source_fields` — 소스별 필드 메타(key,label,type,role,visible,sort_order). role: title/link/published/deadline/summary/none.
- `crawl_specs` — 버전·생성방식(heuristic/manual/self-repair)·활성 플래그. `manual`은 재분석 적용, `self-repair`는 수집 자가복구다. 스펙 jsonb에는 힌트와 입력 시각(`hint`/`hintSetAt`)도 들어 있다.
- `items` — 소스 공유 수집물(title,url,published_at,collected_at,excerpt,attrs jsonb,dedupe_hash,is_baseline,cluster_id).
- `item_states` — 사용자별 read/read_at/starred (공유 items와 분리).
- `subscriptions` — 사용자↔소스: display_name, category_id, paused, tagIds는 `subscription_tags`.
- `categories`(최대 3단계, user 소유), `tags`(user 소유), `keyword_rules`(keywords/exclude/scope/scope_id/action).
- `item_rule_matches` — 수집 시 판정된 규칙 매치(user,item → 최우선 1건).
- `crawl_runs`(수집 이력), `crawl_jobs`(수동 수집 큐), `digest_runs`(발송 이력), `manual_actions`(감사), `user_settings`(다이제스트/마지막 방문 시각).
- `llm_calls` — LLM 호출 이력(purpose/model/토큰/소요시간/성공여부). 일별 상한 판정과 사후 비용 추적용. user·source 삭제 시 `set null`로 이력만 남긴다. 현재 쓰이는 purpose는 `analyze-fields`(등록), `rebuild`(재분석), `self-repair`(자가복구)다.

## 6. 데스크 조합 (`/v1/desk`)

단일 요청으로 초기 화면에 필요한 전부를 내려준다: `now`, `lastVisitAt`, `categories`, `tags`, `subscriptions`, `keywordRules`, `items`(최신순, 기준선 포함, 읽음/별표/규칙매치/데드라인 조인), `clusters`, `meta{lastCollectAt, sourceCount, warnCount, userEmail}`.

- `POST /v1/desk/heartbeat`가 `last_visit_at`을 갱신한다 — "지난번 이후 새 항목" 판정 기준.

## 7. 오류 처리 계약

- `AppError(code, message, status)` → 표준 오류 envelope. 코드는 `api-contracts`의 `errorCodes` 상수를 쓴다.
- `AppError`가 아닌 예외는 `INTERNAL_ERROR`로 치환하고 서버 로그에만 스택을 남긴다.
- Zod 검증 실패 → `VALIDATION_ERROR` + issues를 details에 포함.
- 외부 fetch 실패는 도메인 오류로 변환한다(`URL_UNREACHABLE`, `RATE_LIMITED`, `ROBOTS_DISALLOWED`, `EXTRACTION_FAILED`).

## 9. 보안 설계

- **SSRF**: `assertPublicUrl`이 사설/루프백/링크로컬/멀티캐스트 IP, `.local`/`.internal` 호스트, 인증정보 포함 URL을 차단한다. 리다이렉트 시에도 매 홉 재검사한다.
- **robots**: 도메인별 robots.txt를 파싱·캐시하고 수집 전에 검사한다. 금지 시 link-only로만 등록 가능.
- **SQL**: 모든 외부 값은 파라미터 바인딩. 동적 컬럼/테이블은 허용 목록만.
- **입력**: 경계의 모든 입력(URL, path, query, body, header, env, 외부 응답)은 zod로 검증한다.
- **비밀**: 시크릿 비교는 해시 후 `timingSafeEqual`. 세션·매직링크 토큰은 해시로만 저장.
- **출력**: 에러 envelope에 SQL/스택/프로바이더 원문을 넣지 않는다. 다이제스트 HTML은 이스케이프한다.

## 10. 운영 고려사항

- **마이그레이션**: `database/migrations/myportal/`에 순번 SQL을 추가한다. `schema_migrations`가 적용 여부를 기록해 재실행을 막는다. 적용된 파일은 불변.
- **배포 순서 — 마이그레이션이 먼저다**: `004_fetch_profile.sql`(`sources.fetch_profile` 추가)을 **코드 배포 전에** 적용한다. `findById`가 그 컬럼을 조회하므로, 적용 전에 코드가 배포되면 수집과 구독 조회가 실패한다. 반대 순서(마이그레이션만 먼저)는 안전하다 — 컬럼은 `default '{}'`로 추가되고 이전 코드는 이를 읽지 않는다.
- **실행 시간 한도**: 분석 경로(`/v1/sources/analyze`·`reanalyze`)는 `maxDuration = 120`초를 전제로 시간 예산을 짠다(4-2). 플랜 상한이 이보다 낮으면 `route.ts`의 값과 `run-analysis.ts`의 `PLATFORM_MAX_DURATION_MS`를 함께 낮춰야 한다.
