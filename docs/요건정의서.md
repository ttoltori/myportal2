## 1. 서비스 정의

### 1.1 한 문장 정의

> 한 번 스쳐 간 사이트의 URL만 맡겨두면, 그 사이트가 새로 내놓는 글·공고를 알아서 모아
> **"지난번 이후 무엇이 새로 나왔는가"** 를 한 화면에서 훑게 해주는 개인 통신 데스크.

### 1.2 배경과 문제

1. 인터넷에는 알찬 정보를 꾸준히 갱신하는 사이트가 많지만, 한 번 방문하고 나면 잊힌다.
2. 북마크는 **링크만 보관**할 뿐, 그 사이트에서 **무엇이 새로 올라왔는지** 알려주지 않는다.
3. 북마크 관리자를 여는 행위 자체가 일어나지 않는다. 사용자가 찾아가는 구조는 실패한다.
4. 특히 **AI·로봇·IT 분야의 뉴스와 정부·기관 사업공고**는 양이 방대하고 출처가 흩어져 있어, 사람이 매일 순회하며 확인하는 것이 불가능에 가깝다.
5. 공고성 사이트의 상당수는 **RSS를 제공하지 않는다.** 기존 RSS 리더로는 해결되지 않는다.

### 1.3 목표

| 구분 | 목표 |
|---|---|
| 1차(MVP) | 개발자 본인의 니즈 충족: AI·로봇·IT 뉴스/공고 소스 30~100개를 등록하고, 하루 1~2회 5분 안에 새 소식을 훑고 놓치지 않는다. |
| 2차 | 같은 니즈를 가진 다른 사용자에게 개방 (멀티유저 운영) |

### 1.4 사고방식 (기획 원칙)

`아이디어.txt`의 원칙을 기획 판단 기준으로 삼는다.

- **남들이 크롤링하지 않는 사이트를 크롤링한다.** RSS가 없는 공고 게시판처럼, 기존 리더가 포기한 소스가 핵심 대상이다.
- **사용자가 찾아가지 않는다. 사이트가 사용자에게 온다.** 모든 기능은 "사용자의 수고를 줄이는가"로 평가한다.
- **먼저 내 니즈를 해결한다.** 범용성을 위해 MVP를 부풀리지 않는다.

### 1.5 대상 사용자 (페르소나)

**P1. 개발자 본인 — "과부하된 IT 관찰자"**
- AI 모델 발표, 로봇 산업 뉴스, IT 기술 블로그, 정부 R&D·지원사업 공고를 추적한다.
- 매일 아침/저녁 짧은 시간에 몰아서 확인한다. 넓은 모니터의 PC 환경이 주 사용 환경이다.
- 원하는 것: 중복 없이, 관심 키워드가 걸린 것부터, 공고는 마감 전에.

**P2. (2차) 같은 분야의 실무자·연구자·스타트업 담당자**
- 정부 과제 공고, 경쟁사 블로그, 업계 뉴스를 모니터링해야 하는 사람.

### 1.6 대표 소스 예시 (MVP 검증 대상)

| 분류 | 예시 | 특징 |
|---|---|---|
| AI 기업/연구 블로그 | 모델 개발사 뉴스룸, 연구소 블로그 | RSS 있는 경우 多 |
| 로봇 산업 뉴스 | 로봇 전문 매체 | RSS 있거나 정적 목록 |
| 국내 IT 뉴스/커뮤니티 | IT 전문지, 개발자 뉴스 큐레이션 | 목록 페이지, 정적 HTML |
| 정부·기관 사업공고 | 정보통신 R&D 기관, 창업지원 포털 | **RSS 없음**, 표 형식 목록, 접수기간 필드, 일부 JS 렌더링 |

## 2. 범위

### 2.1 MVP 범위 (In Scope)

1. 사용자 인증 (Supabase Auth, 멀티유저 대비 데이터 구조)
2. URL 등록 및 자동 분석 (목록 페이지 / 상세 페이지 판별)
3. 맞춤형 추출 명세(크롤러) 자동 생성, 수집, 자가 복구
4. 소스별 수집 필드 메타 관리 및 구조 조망
5. 트리 카테고리 + 태그 관리 (이동/병합/분류)
6. 카테고리·태그·소스 자동 제안 (사용자 확인 후 반영)
7. 업데이트 피드 열람 (파일탐색기형 3단 레이아웃, 읽음 상태, 지난 방문 이후 구분)
8. **키워드 규칙** (강조 / 알림 / 뮤트)
9. **일간 다이제스트 이메일**
10. 소스 수집 상태(건강도) 모니터링
11. 중복 기사 묶음, 공고 마감일 뷰 (뉴스·공고 과부하 대응)

### 2.2 향후 과제 (Out of Scope, 필요 시 확장)

| 항목 | 보류 이유 |
|---|---|
| 브라우저 북마크 / OPML 가져오기 | 기존 북마크는 방대하고 비뉴스성 콘텐츠가 많아 처리 부담이 큼 |
| 북마크릿·브라우저 확장 원클릭 등록 | MVP는 웹 화면 URL 입력으로 충분 |
| 페이지 변경 감지 모드 (목록 없는 단일 페이지 본문 diff) | 부모 목록을 찾지 못한 URL은 MVP에서 링크 보관만 |
| RSS/OPML 내보내기, 공개 큐레이션 페이지 | 본인 니즈 충족 후 공유 단계에서 검토 |
| 스마트 폴더(저장된 필터) | 카테고리 + 태그 + 키워드 규칙으로 우선 대응 |
| AI 요약 | 비용 대비 효과 검증 후 도입 |
| 요금제, 사용량 과금 | 2차 공개 시점 |
| 모바일 전용 UI | 넓은 화면의 웹 서비스가 우선 (모바일은 다이제스트 메일로 대응) |

## 3. 용어 정의

| 용어 | 정의 |
|---|---|
| 소스(Source) | 수집 대상이 되는 **목록 페이지 URL** 1개. 여러 사용자가 공유한다. |
| 구독(Subscription) | 사용자가 특정 소스를 자신의 포털에 등록한 관계. 표시 이름, 카테고리, 태그를 사용자별로 가진다. |
| 항목(Item) | 소스에서 수집된 개별 글·공고 1건. 여러 사용자가 공유한다. |
| 추출 명세(Extraction Spec) | 목록 페이지에서 항목과 필드를 뽑아내는 **선언형 규칙(JSON)**. 실행 코드가 아니다. 버전 관리된다. |
| 필드 메타(Source Field) | 소스별로 수집하는 필드의 이름·표시명·타입·역할 정의. |
| 수집 방식(Fetch Strategy) | `rss` / `structured`(JSON-LD 등) / `html`(정적) / `rendered`(헤드리스 렌더링) |
| 기준선(Baseline) | 소스를 처음 수집할 때 이미 존재하던 항목. "새 글"로 취급하지 않는다. |
| 키워드 규칙 | 제목·필드에 특정 단어가 있을 때 강조·알림·뮤트하는 사용자 규칙. |
| 다이제스트 | 지정 시각에 발송하는 새 항목 요약 이메일. |
| 이야기 묶음(Story Cluster) | 여러 소스에서 수집된 사실상 같은 소식을 하나로 묶은 단위. |

## 4. 사용자 시나리오

### S1. 첫 소스 등록
1. 사용자가 정부 기관의 사업공고 목록 URL을 붙여 넣는다.
2. 시스템이 분석 단계(RSS 탐지 → 구조화 데이터 → HTML 분석 → 필요 시 렌더링)를 실시간으로 보여준다.
3. 추출 미리보기 표에 최근 공고 10건과 필드(제목, 공고번호, 접수기간, 담당부서)가 나타난다.
4. 시스템이 카테고리 `공고 > 정부 R&D`, 태그 `AI`, `R&D`를 제안한다. 사용자는 필드 이름 하나를 고치고 확인한다.
5. 기존 공고는 기준선으로 저장되고, 이후 올라오는 공고만 "새 글"이 된다.

### S2. 아침 5분 훑기
1. 사용자가 포털을 연다. 좌측 트리에 카테고리별 새 글 수가 표시된다.
2. 중앙 목록 상단에 "지난 방문(어제 22:10) 이후 47건" 구분선이 보인다.
3. 키워드 규칙에 걸린 항목(예: `휴머노이드`, `LLM 에이전트`)이 강조되어 먼저 보인다.
4. 같은 발표를 다룬 기사 5건은 한 줄로 묶여 "외 4개 소스"로 표시된다.
5. 키보드(j/k)로 이동하며 우측 패널에서 메타 정보를 확인하고, 필요한 것만 원문을 새 탭으로 연다.
6. 카테고리 단위로 "모두 읽음" 처리하고 닫는다.

### S3. 공고 마감 확인
1. 사용자가 `마감 임박` 뷰를 연다.
2. 접수기간 필드를 가진 모든 소스의 공고가 마감일 순으로 정렬되어 D-day와 함께 표시된다.

### S4. 상세 페이지 URL 등록
1. 사용자가 뉴스 기사 1건의 URL을 붙여 넣는다.
2. 시스템이 상세 페이지로 판별하고 부모 목록 후보(섹션 목록, 기자 목록 등)를 찾아 제시한다.
3. 사용자가 후보 하나를 선택하면 S1의 흐름으로 이어진다.
4. 후보가 없으면 "링크로만 보관" 소스로 저장되고 수집하지 않는다.

### S5. 수집 실패와 자가 복구
1. 사이트 개편으로 추출 결과가 0건이 된다.
2. 시스템이 추출 명세를 자동으로 재생성하고, 성공하면 새 버전으로 교체한다.
3. 재생성도 실패하면 소스 상태를 `주의`로 바꾸고 좌측 트리와 소스 관리 화면에 표시한다.

### S6. 다이제스트 수신
1. 매일 07:30에 전날 이후 새 항목 요약 메일을 받는다.
2. 알림 키워드에 걸린 항목, 마감 임박 공고, 카테고리별 새 글 수 순서로 구성된다.

## 5. 기능 요구사항

우선순위: **M**(Must, MVP 필수) / **S**(Should, MVP 포함 목표) / **C**(Could, 여유 시)

### 5.1 인증·계정 (AUTH)

| ID | 요구사항 | 우선 |
|---|---|---|
| AUTH-01 | Supabase Auth 기반 이메일 매직링크 로그인을 제공한다. | M |
| AUTH-02 | 모든 사용자 데이터(구독, 카테고리, 태그, 읽음 상태, 키워드 규칙)는 사용자별로 격리된다. | M |
| AUTH-03 | 사용자 설정: 시간대, 다이제스트 발송 시각, 다이제스트 사용 여부. | M |
| AUTH-04 | MVP에서는 가입을 초대(허용 이메일 목록)로 제한할 수 있다. | S |

### 5.2 소스 등록·분석 (SRC)

| ID | 요구사항 | 우선 |
|---|---|---|
| SRC-01 | 사용자는 URL을 입력하여 소스 등록을 시작한다. | M |
| SRC-02 | URL을 정규화(스킴, 트래킹 파라미터 제거, 후행 슬래시 등)하고, 이미 다른 사용자가 등록한 소스가 있으면 **새로 분석하지 않고 기존 소스를 구독**한다. | M |
| SRC-03 | 시스템은 URL이 **목록 페이지 / 상세 페이지 / 판별 불가** 중 무엇인지 판별한다. | M |
| SRC-04 | 목록 페이지는 수집 방식을 다음 순서로 시도한다: ① RSS/Atom 자동 탐지 → ② 구조화 데이터(JSON-LD 등) → ③ 정적 HTML + LLM 추출 명세 생성 → ④ 헤드리스 렌더링 후 ③. 앞 단계에서 성공하면 뒤 단계는 수행하지 않는다. | M |
| SRC-05 | 분석 진행 단계와 결과(성공/실패/사유)를 사용자에게 단계별로 표시한다. | M |
| SRC-06 | 분석 결과로 **추출 미리보기**(최근 항목 최대 10건 × 필드)를 보여준다. | M |
| SRC-07 | 사용자는 미리보기에서 필드 표시명 변경, 필드 숨김, 필드 역할(제목/링크/게시일/마감일/요약) 지정을 할 수 있다. | M |
| SRC-08 | 상세 페이지는 부모 목록 후보를 탐색한다 (breadcrumb, 상위 경로 절단, 페이지 내 목록형 링크, 표준 링크 태그 등). 후보를 최대 3개 제시하고, 사용자가 선택하면 SRC-04로 진행한다. | M |
| SRC-09 | 부모 후보가 없거나 분석에 실패하면 **링크 전용 소스**로 저장하고 수집하지 않는다. | M |
| SRC-10 | 첫 수집 항목은 기준선으로 저장하고 안읽음으로 만들지 않는다. | M |
| SRC-11 | 사용자는 구독별 표시 이름, 수집 일시정지, 구독 해제를 할 수 있다. 구독자가 0명이 된 소스는 수집을 중지한다. | M |
| SRC-12 | 한 번에 여러 URL(줄바꿈 구분)을 입력해 일괄 분석할 수 있다. | C |

### 5.3 추출 명세·수집 (CRAWL)

| ID | 요구사항 | 우선 |
|---|---|---|
| CRAWL-01 | 추출 명세는 선언형 JSON으로 저장한다 (항목 반복 셀렉터, 필드별 셀렉터·속성·타입·후처리). 생성된 임의 코드는 실행하지 않는다. | M |
| CRAWL-02 | 추출 명세는 버전 관리한다. 어느 버전이 언제 생성·교체되었는지 이력을 남긴다. | M |
| CRAWL-03 | LLM은 **명세 생성 시점과 복구 시점에만** 호출한다. 정기 수집에서는 호출하지 않는다. | M |
| CRAWL-04 | 정기 수집은 작업 큐 방식으로 처리한다. 스케줄러가 주기적으로 수집 대상 소스를 큐에 넣고, 워커가 제한된 건수씩 처리한다. | M |
| CRAWL-05 | 항목 중복은 정규화된 URL 기준으로 판정한다. URL이 없는 항목은 핵심 필드 해시로 판정한다. | M |
| CRAWL-06 | 조건부 요청(ETag, Last-Modified)을 사용해 변경 없는 페이지의 처리 비용을 줄인다. | M |
| CRAWL-07 | robots.txt를 준수하고, 도메인별 최소 요청 간격을 둔다. 식별 가능한 User-Agent를 사용한다. | M |
| CRAWL-08 | **자가 복구**: 추출 결과가 0건이거나 필수 필드(제목, 링크) 누락률이 임계치를 넘으면 명세 재생성을 1회 시도한다. 성공 시 새 버전으로 교체하고, 실패 시 소스 상태를 `주의`로 전환한다. | M |
| CRAWL-09 | **적응형 수집 주기**: 소스의 최근 갱신 빈도에 따라 수집 주기를 조정한다 (예: 최소 30분 ~ 최대 24시간). 사용자가 소스별로 고정 주기를 지정할 수도 있다. | S |

## 7. 데이터 요구사항 (개념 모델)

상세 스키마는 설계 단계에서 확정한다. 모든 테이블은 `myportal` 스키마에 둔다.

```text
[공유 영역: 크롤링 결과는 사용자 간 공유]
sources            소스(정규화 URL, 종류, 수집 방식, 상태, 수집 주기, 다음 수집 시각)
source_fields      소스별 필드 메타(키, 표시명, 타입, 역할, 순서)
crawl_specs        추출 명세 버전(명세 JSON, 생성 방식, 활성 여부)
crawl_runs         수집 실행 이력
crawl_jobs         수집 작업 큐
items              수집 항목(공통 컬럼 + 가변 속성 JSONB, 정규화 URL, 해시, 기준선 여부)
story_clusters     이야기 묶음

[사용자 영역: 사용자별 격리]
users(Supabase Auth 연동) / user_settings
categories         트리(부모 ID, 정렬 순서)
tags
subscriptions      사용자-소스 구독(표시 이름, 카테고리, 일시정지)
subscription_tags
item_states        사용자-항목 상태(읽음, 별표, 읽은 시각)
keyword_rules      키워드 규칙
item_rule_matches  규칙 매칭 결과
digest_runs        다이제스트 발송 이력
visit_marks        지난 방문 시각
```

데이터 원칙:
- 항목 본문 전체를 저장하지 않는다 (CRAWL-11).
- 공유 영역의 데이터는 API를 통해 해당 소스를 구독한 사용자에게만 노출한다.
- API 응답에 DB Row를 그대로 노출하지 않는다 (`CLAUDE.md` §12, §15).

## 8. 비기능 요구사항

### 8.2 실행 환경·운영 (Vercel 단일 운영)
| ID | 요구사항 |

| NFR-O1 | 모든 백엔드 로직(수집, 명세 생성, 키워드 판정, 묶음, 다이제스트)은 Vercel 함수에서 실행한다. Supabase Function/Trigger/Edge Function에 업무 로직을 두지 않는다. |
| NFR-O2 | 함수 실행 시간 제한을 고려해 수집은 큐 기반 소량 배치로 나누어 처리한다. 작업 할당은 DB 잠금(`FOR UPDATE SKIP LOCKED`)으로 중복 처리를 막는다. |
| NFR-O3 | 헤드리스 렌더링은 서버리스용 경량 Chromium을 사용하며, 렌더링 필요 소스는 별도 큐·낮은 동시성으로 처리한다. |

| NFR-O5 | 스케줄러·워커 엔드포인트는 공유 비밀 헤더로 보호한다. |
| NFR-O6 | 핵심 로직은 Vercel SDK·전용 환경변수에 의존하지 않고, 일반 Node.js 환경에서도 실행 가능해야 한다. |

### 8.3 LLM 사용
| ID | 요구사항 |
|---|---|
| NFR-L1 | LLM은 추출 명세 생성·복구, 페이지 종류 판별 보조, 카테고리·태그 제안에만 사용한다. |
| NFR-L2 | LLM 출력은 Zod 스키마로 검증하고, 검증 실패 시 재시도 1회 후 실패 처리한다. |
| NFR-L3 | LLM 입력 HTML은 스크립트·스타일 제거, 크기 절단 등 전처리로 토큰 사용량을 줄인다. |
| NFR-L4 | 사용자별·일별 LLM 호출 상한을 둔다 (비용 폭주 방지). |

### 8.4 보안·준법
| ID | 요구사항 |
|---|---|
| NFR-S1 | 모든 외부 입력(URL, 규칙, 설정)은 Zod로 검증한다. |
| NFR-S2 | **SSRF 방지**: 사설망·루프백·메타데이터 주소, 비 HTTP(S) 스킴으로의 요청을 차단한다. 리다이렉트 후 주소도 재검증한다. |
| NFR-S3 | 수집한 HTML·텍스트는 화면 출력 시 이스케이프한다. 원본 HTML을 그대로 렌더링하지 않는다. |
| NFR-S4 | robots.txt 준수, 요청 간격 제한, 본문 비저장으로 저작권·서비스 약관 위험을 최소화한다. |
| NFR-S5 | 오류 응답에 내부 SQL, 스택, 외부 사이트 원본 오류를 노출하지 않는다. |

### 8.5 가용성·관측
| ID | 요구사항 |
|---|---|
| NFR-A1 | 수집 성공률, 소스 상태별 수, 큐 적체량, LLM 호출 수를 로그로 확인할 수 있어야 한다. |
| NFR-A2 | 개별 소스의 실패가 다른 소스 수집에 영향을 주지 않는다. |

### 8.6 사용성
| ID | 요구사항 |
|---|---|
| NFR-U1 | 1280px 이상 넓은 화면을 기본으로 설계하고, 1920px 이상에서 3단을 모두 활용한다. |
| NFR-U2 | 모든 핵심 조작은 키보드로 가능해야 한다. |
| NFR-U3 | 라이트/다크 테마를 지원한다. |

## 9. 오류 코드 초안

클라이언트는 메시지가 아니라 코드로 분기한다 (`CLAUDE.md` §15).

| 코드 | 의미 |
|---|---|
| `INVALID_URL` | URL 형식 오류 또는 허용되지 않는 주소 |
| `URL_UNREACHABLE` | 대상 사이트 접근 실패 |
| `ROBOTS_DISALLOWED` | robots.txt에서 수집 금지 |
| `PAGE_TYPE_UNKNOWN` | 목록/상세 판별 불가 |
| `PARENT_NOT_FOUND` | 상세 페이지의 부모 목록을 찾지 못함 |
| `EXTRACTION_FAILED` | 추출 명세 생성 실패 |
| `ALREADY_SUBSCRIBED` | 이미 구독 중인 소스 |
| `SOURCE_NOT_FOUND` | 소스 없음 또는 접근 권한 없음 |
| `CATEGORY_NOT_FOUND` | 카테고리 없음 |
| `CATEGORY_DEPTH_EXCEEDED` | 카테고리 깊이 제한 초과 |
| `CATEGORY_CYCLE` | 자기 하위로 이동 시도 |
| `RATE_LIMITED` | 수동 수집·분석 호출 간격 제한 |
| `LLM_QUOTA_EXCEEDED` | 일일 LLM 호출 상한 초과 |
| `UNAUTHORIZED` / `FORBIDDEN` | 인증·권한 오류 |

## 10. 제약사항과 전제

1. 기술 스택과 구조는 `CLAUDE.md`를 따른다 (Next.js + Hono + Supabase PostgreSQL + `pg`, ORM 미사용).
2. 로그인이 필요한 사이트, 유료 벽 뒤의 콘텐츠, CAPTCHA가 있는 사이트는 수집 대상에서 제외한다.
3. 무한 스크롤·"더보기" 버튼으로만 목록이 나오는 사이트는 첫 화면에 보이는 항목만 수집한다.
4. 사이트가 robots.txt로 금지하면 링크 전용으로만 보관한다.

## 13. 성공 지표 (본인 사용 기준)

- 등록 성공률: 입력한 목록 URL 중 사람 개입 없이 수집에 성공한 비율 **80% 이상**
- 아침 확인 시간: 새 소식 확인 **5분 이내**
- 놓친 공고: 관심 공고의 마감 후 발견 **0건**
- 수집 안정성: 주간 `실패` 상태 소스 비율 **5% 이하**
