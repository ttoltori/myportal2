# myportal 개발자 가이드

이 문서는 이 프로젝트를 처음 열어보는 개발자가 아무 배경지식 없이도 로컬에서 실행하고, 코드를 이해하고, 수정할 수 있도록 안내하는 문서다. "이미 알고 있겠지"라고 생략하지 않고 개념부터 설명한다.

## 0. myportal이 무엇인가

`myportal`은 관심 있는 URL(뉴스 사이트, 정부 공고 페이지, 회사 블로그 등)을 등록해두면, 서버가 주기적으로 그 페이지를 다시 방문해서 **지난번 확인 이후 새로 올라온 글/공고**만 모아서 보여주는 개인용 모니터링 서비스다. 신문 편집국(데스크)에서 여러 통신사 기사를 훑어보는 느낌의 UI를 사용한다.

기술적으로는 하나의 Next.js 프로젝트 안에:

- **프론트엔드**(화면, React)
- **백엔드 API**(Hono로 만든 REST API)

가 함께 들어 있다. 즉 프론트엔드 저장소 따로, 백엔드 저장소 따로가 아니라 **`myportal` 폴더 하나만 있으면 전체가 다 있다.** 로컬에서는 `pnpm dev` 한 번으로 화면과 API 서버가 동시에 켜진다(port 3001).

데이터는 Supabase가 제공하는 PostgreSQL 데이터베이스에 저장한다. Supabase는 "관리형 PostgreSQL + 부가기능(인증, 파일저장 등)을 제공하는 서비스"라고 생각하면 된다. 이 프로젝트는 Supabase의 **데이터베이스(PostgreSQL)** 기능만 필수로 사용하고, Supabase의 로그인(Auth) 기능은 선택적으로만 사용한다(§3-4 참고).

## 1. 사전 준비물

로컬에서 처음 실행하기 전에 아래 3가지가 필요하다. 이미 익숙하다면 건너뛰어도 좋다.

### 1-1. Node.js와 pnpm

- **Node.js**: JavaScript를 서버에서 실행할 수 있게 해주는 런타임. 버전 20 이상이 필요하고, **22 버전을 권장**한다(22부터 `.env` 파일을 코드 한 줄로 읽어들이는 `process.loadEnvFile` 기능이 내장돼 있어서 이 프로젝트의 CLI 스크립트들이 이를 사용한다).
  - 설치 확인: 터미널에 `node -v` 입력 → `v22.x.x` 같은 값이 나오면 OK.
  - 없다면 [nodejs.org](https://nodejs.org)에서 LTS(22.x) 버전을 설치한다.
- **pnpm**: `npm`과 같은 역할(패키지 설치 도구)을 하지만, 이 프로젝트처럼 여러 개의 하위 패키지(`packages/*`)를 한 저장소에서 관리하는 "모노레포" 구조를 더 잘 지원한다.
  - 설치: `npm install -g pnpm`
  - 확인: `pnpm -v`

### 1-2. Supabase 프로젝트 (데이터베이스)

이 프로젝트는 로컬 PC에 Docker로 PostgreSQL을 직접 띄우지 않는다. **항상 Supabase가 호스팅하는 PostgreSQL을 사용한다**(개발원칙 `CLAUDE.md` §1). 이유는 로컬 환경과 배포 환경(Vercel)의 데이터베이스 설정 차이를 없애기 위해서다.

1. [supabase.com](https://supabase.com) 에 가입한다(GitHub 계정으로 가입 가능).
2. 대시보드에서 **New project**를 눌러 프로젝트를 하나 만든다.
   - Project name: 아무 이름이나 (예: `myportal-dev`)
   - Database Password: 임의로 정하고 **꼭 메모해둔다**(뒤에서 연결 문자열에 그대로 들어간다).
   - Region: 가까운 지역 선택 (예: Northeast Asia, Seoul)
3. 프로젝트가 생성되면(1~2분 소요) 왼쪽 메뉴에서 **Project Settings → Database**로 이동한다.
4. **Connection string** 항목에서 URI 형식의 문자열을 확인할 수 있다. 두 가지 방식이 있는데:
   - **Session pooler**(포트 6543): 커넥션을 서버리스/짧은 연결에 최적화한 방식. 로컬 개발 및 Vercel 배포에 **이 방식을 권장**한다.
   - **Direct connection**(포트 5432): 데이터베이스에 직접 붙는 방식. 마이그레이션처럼 무거운 작업에도 쓸 수 있지만 동시 연결 수 제한이 낮다.
   - 화면에 나온 문자열 안의 `[YOUR-PASSWORD]` 부분을 2번에서 정한 비밀번호로 바꿔야 한다.
5. 이렇게 얻은 문자열이 `DATABASE_URL`이다. (자세한 형식은 §3-1 참고)

> 이미 만들어둔 Supabase 프로젝트가 있다면 그걸 재사용해도 된다. myportal은 `myportal`이라는 전용 스키마(네임스페이스) 안에만 테이블을 만들기 때문에, 같은 프로젝트를 다른 서비스와 공유해도 테이블 이름이 충돌하지 않는다.

### 1-3. 저장소 코드

이 문서를 보고 있다면 이미 `myportal` 폴더를 가지고 있을 것이다. 없다면 `git clone`으로 받는다.

## 2. 처음 실행하기 (단계별)

```bash
# 0) 프로젝트 폴더로 이동
cd myportal

# 1) 의존성 설치 — package.json과 packages/*에 정의된 모든 패키지를 내려받는다
pnpm install
```

`pnpm install` 실행 시 다음과 같은 경고가 보일 수 있는데 **무시해도 된다** — `.npmrc`에 `@ttoltori` 스코프 패키지용 GitHub 레지스트리 인증 설정이 있지만, 실제로는 `packages/database`, `packages/api-client-core`, `packages/hono-api-kit`에 로컬 복사본이 있어서 그 인증 없이도 설치가 완료된다.

```
[WARN] Ignored project-level auth setting "//npm.pkg.github.com/:_authToken" ...
```

```bash
# 2) 환경변수 파일 만들기
cp .env.example .env.local
```

`.env.local`은 나만의 로컬 설정 파일이며 `.gitignore`에 등록되어 있어 git에 올라가지 않는다(비밀번호가 들어있으므로 당연히 커밋하면 안 된다). 파일을 열어서 최소한 아래 값을 채운다. **각 값이 정확히 무엇이고 어디서 구하는지는 §3(환경변수 상세 설명)에 전부 정리되어 있으니, 처음이라면 지금 §3을 먼저 읽고 오는 것을 추천한다.**

```env
# 1-2에서 Supabase 대시보드에서 복사한 연결 문자열 (비밀번호 채워 넣기)
DATABASE_URL=postgres://postgres.xxxxxxxx:<DB비밀번호>@aws-0-ap-northeast-2.pooler.supabase.com:6543/postgres

# 아무 문자열이나 길게 입력 (내부 API 보호용 비밀키, 직접 만들어서 채우면 됨)
INTERNAL_API_SECRET=아무렇게나-길게-만든-임의의-문자열

# 로컬 개발에서는 true로 둔다 — 실제 메일을 보내지 않고 화면에 로그인 링크를 바로 보여준다
AUTH_DEV_MODE=true
```

`SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY`는 지금 단계에서는 **비워둬도 된다**. `AUTH_DEV_MODE=true`이면 Supabase Auth 없이도 로그인할 수 있다 (§3-4에서 자세히 설명).

```bash
# 3) 데이터베이스 테이블 생성
pnpm db:migrate
```

이 명령은 `database/migrations/myportal/*.sql` 파일들을 순서대로 실행해서, 방금 연결한 Supabase 데이터베이스 안에 `myportal` 스키마와 테이블들(`users`, `sources`, `items` 등)을 만든다. 이미 적용된 마이그레이션은 `myportal.schema_migrations` 테이블에 기록되므로 여러 번 실행해도 안전하다(중복 적용 안 됨).

```bash
# 4) 개발용 사용자 계정 생성 (선택이지만 권장)
pnpm db:seed
```

`dev@myportal.local`이라는 사용자와 기본 "미분류" 카테고리를 미리 만들어둔다. (사실 로그인만 해도 사용자는 자동 생성되지만, 시드를 해두면 바로 쓸 수 있는 카테고리까지 준비된다.)

```bash
# 5) 개발 서버 실행
pnpm dev
```

터미널에 `Ready`가 뜨면 브라우저에서 <http://localhost:3001> 을 연다. 로그인 화면(`/login`)으로 자동 이동한다.

### 2-1. 로그인해보기 (개발 모드)

1. `/login` 화면에서 이메일 주소를 아무거나 입력한다(예: `dev@myportal.local`). 실제로 메일이 오는 게 아니라 `.env.local`의 `ALLOWED_EMAILS`가 비어있는 한 어떤 이메일이든 통과한다.
2. "로그인 링크 보내기"를 누르면, `AUTH_DEV_MODE=true`이기 때문에 실제 메일 발송 대신 화면에 **개발용 로그인 링크**가 바로 표시된다(서버 콘솔 로그에도 같은 링크가 출력된다).
3. 그 링크를 클릭하면 세션 쿠키(`myportal_session`)가 발급되고 메인 데스크 화면으로 이동한다.

여기까지 되면 로컬 개발 환경 준비가 끝난 것이다.

### 2-2. 수집 기능 확인해보기

myportal의 핵심 기능인 "URL 등록 → 주기적 수집"을 테스트하려면:

1. 로그인 후 `/add-source`에서 RSS가 있는 사이트 URL(예: 아무 뉴스 사이트)을 입력하고 분석한다.
2. 분석 결과를 확인하고 저장하면 소스가 등록되고, 등록 시점 기준 최근 글들이 "기준선(baseline)"으로 들어간다. 기준선 항목도 데스크 목록에 보이지만 읽은 것으로 처리되어 "새 글" 카운트에는 잡히지 않는다.
3. 이후 새 글이 올라왔는지 확인하려면 수집을 한 번 더 돌려야 하는데, 로컬에서는 자동으로 도는 크론이 없으므로 수동으로 아래처럼 실행한다.

```bash
# 방법 A: CLI 워커 스크립트로 한 번 수집 (등록된 소스 중 수집 시각이 된 것들을 처리)
pnpm crawl:once

# 수집 시각과 무관하게 모든 구독 소스를 즉시 수집 (테스트용)
pnpm crawl:once --force

# 60초 간격으로 반복 수집하고 싶다면
pnpm crawl:watch

# 방법 B: 운영(Vercel cron)과 동일한 HTTP 엔드포인트를 직접 호출
curl -X POST http://localhost:3001/api/v1/internal/crawl-tick \
  -H "x-internal-secret: $INTERNAL_API_SECRET"

# 다이제스트(요약 메일) 발송 로직도 같은 방식으로 확인 가능
curl -X POST http://localhost:3001/api/v1/internal/digest-tick \
  -H "x-internal-secret: $INTERNAL_API_SECRET"
```

`$INTERNAL_API_SECRET`은 `.env.local`에 넣은 값과 반드시 같아야 한다(그렇지 않으면 401 오류).

### 2-3. 이미 등록한 소스를 다시 분석하기

소스 상세 화면(`/sources/[id]`)의 **'다시 분석'** 버튼이다.

**언제 쓰나**

- `LLM_API_KEY`를 설정하기 **전에** 등록한 소스. 그때는 제목·링크·게시일만 추출됐으므로, 다시 분석하면 접수기간·주최기관 같은 필드가 붙는다.
- 사이트가 개편되어 수집이 0건이 되거나 필드가 비어버린 소스.
- 자동 추정이 메뉴 등 엉뚱한 영역을 잡은 소스 — 패널에서 '목록 항목 힌트'를 바꿔 다시 실행할 수 있다.

**흐름**

1. '다시 분석'을 누르면 그 자리에 패널이 펼쳐지고, 분석 단계와 추출 미리보기가 나온다. **이 단계에서는 DB가 전혀 바뀌지 않는다** — '취소'를 눌러도 되돌릴 것이 없다.
2. 필드의 표시명·타입·역할·표시여부를 등록 화면과 똑같이 고칠 수 있다.
3. '적용'을 누르면 새 스펙이 저장되고, **이미 수집된 항목에 새 필드 값이 백필된다.** 결과는 `버전 N 적용 · 백필 N건 · 신규 N건`으로 표시된다.

**보존되는 것**: 읽음·별표, 표시 이름·카테고리·태그, 수집 이력, 스펙 이력. 일시정지도 적용이 풀지 않는다. 그래서 소스를 지우고 재등록하는 것보다 낫다 — 애초에 구독 해제는 소스를 지우지 않고, 같은 URL을 다시 넣으면 이미 등록된 소스로 보고 분석을 건너뛴다.

**한계**

- 백필은 **지금 목록 페이지에 남아 있는 항목까지만** 닿는다(보통 수십 건). 목록에서 이미 내려간 오래된 항목은 되돌릴 소스가 없어 새 필드가 빈 채로 남는다.
- `fetch_strategy='link'`(robots 금지) 소스는 수집 자체를 하지 않으므로 버튼이 비활성이다.
- `source_fields`는 **소스 단위로 공유된다.** 같은 소스를 구독한 다른 사용자의 데스크 라벨도 함께 바뀐다. 누가 언제 적용했는지는 `myportal.manual_actions`에 `apply-spec`으로 남는다.
- 재분석은 LLM을 호출하므로 일별 상한(`LLM_DAILY_LIMIT`)을 소모한다. 한도를 넘으면 분석 단계에 경고가 뜨고 휴리스틱 결과만 나온다.


## 3. 환경변수 완전 설명

`.env.local`(로컬용) / Vercel 프로젝트 설정(배포용)에 들어가는 모든 환경변수를 하나씩 설명한다. 표만 보고 넘어가지 말고, 필요한 값은 아래 각 항목을 참고해 정확히 채워 넣자.

### 3-1. 데이터베이스

#### `DATABASE_URL` (필수)

- **의미**: 애플리케이션이 접속할 PostgreSQL 서버의 주소, 계정, 비밀번호, 데이터베이스 이름을 하나의 문자열로 표현한 것. `postgres://사용자:비밀번호@호스트:포트/DB이름` 형태다.
- **왜 필요한가**: 이 값이 없으면 서버가 아예 시작되지 않는다(`env.ts`의 `validateEnv()`가 앱 시작 시 검사한다).
- **어떻게 구하는가**: §1-2에서 만든 Supabase 프로젝트의 **Project Settings → Database → Connection string** 화면에서 복사한다. 반드시 `[YOUR-PASSWORD]` 부분을 실제 비밀번호로 바꿔야 한다.
- **예시**: `postgres://postgres.abcijklmno:mySecretPass1!@aws-0-ap-northeast-2.pooler.supabase.com:6543/postgres`
- **주의**: 비밀번호에 `@`, `/`, `#` 같은 특수문자가 들어가면 URL 인코딩이 필요할 수 있다(예: `@` → `%40`). Supabase 대시보드가 만들어주는 문자열을 그대로 복사하면 이미 인코딩되어 있는 경우가 많다.
- **로컬과 배포에서 값이 다를 수 있다**: 로컬 개발 DB와 운영(프로덕션) DB를 분리하고 싶다면 Supabase 프로젝트를 2개(dev/prod) 만들어서 각각의 `DATABASE_URL`을 로컬 `.env.local`과 Vercel 환경변수에 따로 넣으면 된다.

### 3-2. 앱 기본 설정

#### `APP_BASE_URL`

- **의미**: 이 애플리케이션 자기 자신에 접근할 수 있는 기준 URL. 로그인 메일의 링크를 만들 때(`{APP_BASE_URL}/api/v1/auth/confirm?token=...`)와, 크롤러가 상대방 서버에 자신을 알릴 때 User-Agent 문자열(`myportal-bot/0.1 (+APP_BASE_URL)`)에 사용된다.
- **기본값**: `http://localhost:3001` (로컬에서는 이 기본값으로 충분해서 굳이 설정하지 않아도 된다)
- **배포 시**: Vercel에 배포하면 실제 도메인(예: `https://myportal.vercel.app`)으로 반드시 바꿔줘야 한다. 그렇지 않으면 메일로 보내는 로그인 링크가 `localhost`를 가리키게 된다.

#### `NEXT_PUBLIC_API_URL`

- **의미**: 브라우저(프론트엔드)가 API를 호출할 때 사용하는 기준 주소. `NEXT_PUBLIC_` 접두사가 붙은 환경변수는 Next.js가 빌드 시점에 브라우저로 전달되는 코드에 그대로 박아넣는다(서버만 아는 비밀값을 여기 넣으면 안 되는 이유).
- **기본값**: `http://localhost:3001/api` — 이 프로젝트는 프론트와 백엔드가 같은 서버에 있으므로 로컬에서는 신경 쓸 필요가 거의 없다.
- **필요한 경우**: 프론트엔드와 API가 다른 도메인에 배포되는 특수한 구조로 바꾸는 경우에만 조정한다.

#### `LOG_LEVEL`

- **의미**: 로그 상세도를 표시하기 위해 예약된 값(`info` 기본). 현재 코드베이스에서는 값만 읽어들일 뿐 실제로 로그 필터링에 사용하는 곳은 없다 — 향후 구조화 로깅을 도입할 때 쓰기 위한 자리로 남겨둔 값이다. 신경 쓰지 않아도 된다.

### 3-3. 로그인/세션

#### `ALLOWED_EMAILS`

- **의미**: 로그인을 허용할 이메일 주소를 쉼표(,)로 구분해서 나열. 예: `me@gmail.com,teammate@company.com`
- **기본값**: 비워두면(빈 문자열) **모든 이메일 주소로 로그인 가능**. 개인용 서비스이므로 운영 환경에서는 자기 이메일만 넣어두는 것을 권장한다.

#### `AUTH_DEV_MODE`

- **의미**: 로그인 방식을 결정하는 스위치.
  - `true`(기본값): 매직링크(로그인 링크)를 실제 메일로 보내지 않고, API 응답과 서버 콘솔 로그에 링크를 그대로 노출한다. **로컬 개발 전용.**
  - `false`: 아래 3-4의 Supabase Auth 설정이 있으면 그것을 사용해서 실제로 메일을 보낸다. 설정이 없다면 서버 콘솔에 링크만 출력한다(메일은 안 감).
- **주의**: 운영(배포) 환경에서는 반드시 `false`로 바꿔야 한다. `true`인 채로 배포하면 다른 사람이 아무 이메일이나 입력해도 로그인 링크가 API 응답에 그대로 노출되어 **누구나 로그인할 수 있는 심각한 보안 문제**가 된다.

#### `SESSION_TTL_DAYS`

- **의미**: 로그인 세션(쿠키)의 유효 기간(일 단위). 기본 30일. 이 기간이 지나면 다시 로그인해야 한다.

### 3-4. Supabase Auth (선택)

#### `SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY`

- **의미**: myportal이 자체 구현한 매직링크 대신, Supabase가 제공하는 인증 시스템(Supabase Auth)으로 실제 로그인 메일을 발송하고 싶을 때 사용한다.
- **필요한가?**: **필수 아님.** `AUTH_DEV_MODE=true`이면 이 값이 없어도 로그인이 된다(자체 매직링크 사용). 이 값은 `AUTH_DEV_MODE=false`로 배포하면서 "직접 SMTP를 설정하기 귀찮으니 Supabase가 메일을 대신 보내주면 좋겠다"는 경우에만 채운다.
- **어떻게 구하는가**:
  1. Supabase 대시보드 → 해당 프로젝트 → **Project Settings → API**로 이동.
  2. `Project URL` 값을 `SUPABASE_URL`에 넣는다 (예: `https://abcijklmno.supabase.co`).
  3. `service_role` 키(비밀, `anon` 키가 아님!)를 `SUPABASE_SERVICE_ROLE_KEY`에 넣는다.
- **주의**: `service_role` 키는 Supabase의 모든 보안 규칙(RLS)을 우회할 수 있는 매우 강력한 키다. **절대 프론트엔드 코드나 `NEXT_PUBLIC_*` 변수에 넣지 말고**, 서버 환경변수로만 다뤄야 한다. 이 프로젝트에서도 서버 코드(`src/server/features/auth/auth.ts`)에서만 사용한다.
- **동작 방식**: `SUPABASE_URL`/`SUPABASE_SERVICE_ROLE_KEY`가 모두 설정되어 있고 `AUTH_DEV_MODE=false`일 때만 실제로 Supabase Auth API(`/auth/v1/otp`)를 호출해서 메일을 보낸다. 사용자가 메일의 링크를 클릭하면 `/auth/callback` 페이지가 Supabase의 access token을 받아 `/api/v1/auth/session`으로 넘기고, 서버가 그 토큰을 검증한 뒤 myportal 자체 세션 쿠키를 발급한다.

### 3-5. 내부 API 보호

#### `INTERNAL_API_SECRET`

- **의미**: `/api/v1/internal/*` 경로(크롤 실행, 다이제스트 발송 트리거)를 아무나 호출하지 못하도록 막는 공유 비밀키. 이 경로들은 로그인 세션이 아니라 이 비밀키로만 인증한다(스케줄러/크론이 사람이 아니라 서버이기 때문).
- **어떻게 값을 정하는가**: 무작위로 긴 문자열을 직접 만들면 된다. 예를 들어 터미널에서 `openssl rand -hex 32` 를 실행해서 나온 값을 붙여넣어도 좋다.
- **호출 방법**: 헤더에 `x-internal-secret: <값>` 또는 `Authorization: Bearer <값>` 중 하나를 넣어서 호출한다(Vercel Cron은 `Authorization: Bearer` 방식으로 호출하므로 두 방식을 모두 지원한다).
- **배포 시 주의**: 로컬 값과 운영 값을 다르게 설정하고, 운영 값은 절대 코드/문서에 남기지 않는다.

### 3-6. 수집(크롤링)

#### `CRAWL_USER_AGENT`

- **의미**: myportal이 다른 사이트에 접속할 때 자신을 소개하는 HTTP User-Agent 문자열. 상대 서버 로그에 "이 요청은 myportal 봇이 보낸 것"이라고 표시된다.
- **기본값**: 비워두면 `myportal-bot/0.1 (+APP_BASE_URL)` 형태로 자동 생성된다.
- **바꿔야 하는 경우**: 특정 사이트가 자체 User-Agent를 요구하거나 차단할 때만 조정하면 된다. 보통은 그대로 둔다.

#### `CHROMIUM_PATH`

- **의미**: JavaScript로 내용을 채우는 사이트(초기 HTML에 목록이 없는 페이지)를 수집할 때 사용하는 헤드리스 브라우저의 실행 파일 경로. 소스 등록 분석에서 정적 추출이 실패하거나 힌트 문자열을 못 찾으면 브라우저 렌더링을 자동으로 재시도하고, 성공하면 그 소스는 이후 수집에도 브라우저를 쓴다(`spec.render=true`).
- **비워두면**: 로컬에 설치된 Chrome/Chromium을 자동으로 찾거나 `playwright` 패키지의 브라우저를 사용한다. 로컬 개발에서는 보통 Chrome이 이미 설치되어 있으므로 **비워둬도 동작**한다.
- **값을 넣어야 하는 경우**: 브라우저를 찾지 못해 렌더링이 실패한다는 오류가 나올 때만. Chrome 설치 경로를 직접 지정한다(예: `C:\Program Files\Google\Chrome\Application\chrome.exe`).
- **Vercel 배포**: 서버리스 환경에서는 `@sparticuz/chromium`이 번들된 경량 Chromium을 자동으로 사용하므로 이 변수는 설정하지 않는다.

#### `LLM_API_BASE`, `LLM_API_KEY`, `LLM_MODEL`

- **의미**: 소스 등록 시 목록 항목에서 뽑아낼 **추가 필드(접수기간·주최기관·지원금액 등)의 CSS 셀렉터를 LLM이 추론**하게 하는 설정이다. DOM 휴리스틱(`generateSpec`)은 항목 위치는 잘 찾지만 필드 셀렉터는 만들지 못해 제목·링크·게시일만 추출된다. LLM이 그 빈자리를 메운다.
- **값**:
  - `LLM_API_BASE` — 비우면 `https://api.openai.com/v1`. OpenAI 호환 엔드포인트(Azure OpenAI, 로컬 vLLM 등)를 쓰려면 여기에 넣는다.
  - `LLM_API_KEY` — OpenAI API 키. <https://platform.openai.com/api-keys>에서 발급한다.
  - `LLM_MODEL` — 비우면 `gpt-4o-mini`.
- **비워두면**: 기능이 꺼지고 **분석 결과가 LLM 도입 이전과 완전히 동일하다.** 등록 화면의 '`AI 필드 분석`' 단계가 "AI 분석이 설정되지 않았습니다 — 건너뜀"으로 표시될 뿐, 서버 시작이나 소스 등록은 전혀 영향받지 않는다. 사실상 이 키가 기능 플래그다.
- **호출 시점**: 소스 등록 분석, '명세 다시 만들기', 수집 자가복구 **세 곳뿐**이다. 정기 수집은 저장된 셀렉터를 재사용하므로 LLM을 호출하지 않는다 — 소스당 비용이 1회로 고정된다.
- **안전장치**: LLM이 돌려준 셀렉터는 저장 전에 실제로 실행해 채움률을 확인한다(30% 미만이면 그 필드를 버린다). 타임아웃·오류·한도 초과는 모두 분석 단계의 경고로만 남고 휴리스틱 결과가 그대로 쓰인다.

#### `LLM_DAILY_LIMIT`, `LLM_DAILY_LIMIT_SYSTEM`

- **의미**: 일별 LLM 호출 상한(비용 폭주 방지). `myportal.llm_calls`에 쌓인 당일 성공 호출 수로 판정한다.
- **기본값**: 사용자별 `50`, 시스템 경로(수집 자가복구 등) `200`.
- **초과 시**: 호출을 건너뛰고 분석 단계에 "일별 AI 분석 한도를 초과했습니다"를 남긴다. 분석 자체는 성공한다.
- **참고**: 상한 판정 쿼리가 DB 오류로 실패하면 **호출을 차단한다**(fail-closed). 판정 불가 상태에서 통과시키면 상한의 목적이 사라지기 때문이다.
- **비용 확인**: `select purpose, count(*), sum(prompt_tokens), sum(completion_tokens) from myportal.llm_calls where created_at >= current_date group by purpose;`

### 3-7. 다이제스트(요약 메일)

#### `SMTP_URL`

- **의미**: 다이제스트(구독 요약) 메일을 실제로 발송하기 위한 SMTP 서버 접속 정보. `nodemailer.createTransport(SMTP_URL)`에 그대로 전달되는 연결 문자열이다.
- **형식**: `smtps://사용자:비밀번호@호스트:465` 또는 `smtp://사용자:비밀번호@호스트:587` 형태.
- **비워두면**: 다이제스트를 "보낸 것으로" `digest_runs` 테이블에 `queued` 상태로만 기록하고, 실제 메일은 나가지 않는다. 대신 화면의 미리보기 API로 어떤 내용이 나갈지 확인할 수 있다. **로컬 개발에서는 비워둬도 기능 확인에 지장 없다.**
- **어떻게 구하는가** (실제 메일 발송을 테스트하고 싶다면 아래 중 하나 선택):
  - **Gmail로 테스트**: Google 계정에서 "앱 비밀번호"를 발급받아 `smtps://내메일%40gmail.com:앱비밀번호@smtp.gmail.com:465` 형태로 사용. (일반 로그인 비밀번호는 동작하지 않는다. 2단계 인증을 켠 뒤 앱 비밀번호를 발급해야 한다.)
  - **Mailtrap** 같은 이메일 테스트 서비스: 실제 수신자에게 보내지 않고 가짜 받은편지함에서 내용을 확인할 수 있어 개발 중 안전하게 테스트하기 좋다. 가입 후 제공되는 SMTP 자격증명을 그대로 조합한다.
  - **운영 환경**: Resend, SendGrid, Amazon SES 등 트랜잭션 메일 서비스의 SMTP 자격증명을 사용하는 것을 권장한다.

#### `MAIL_FROM`

- **의미**: 다이제스트 메일의 발신자로 표시될 이름과 주소. 형식: `표시이름 <이메일주소>`
- **기본값**: `myportal <no-reply@myportal.local>`
- **주의**: 실제 발송을 하려면(즉 `SMTP_URL`을 설정했다면) 사용하는 SMTP 서비스가 이 발신 주소를 허용하는지 확인해야 한다(대부분의 서비스는 인증된 도메인의 주소만 발신 허용).

### 3-8. `SEED_EMAIL` (선택, `.env.example`에는 없음)

- **의미**: `pnpm db:seed` 실행 시 만들어질 개발용 계정의 이메일 주소.
- **기본값**: 지정하지 않으면 `dev@myportal.local`.
- **사용법**: `.env.local`에 `SEED_EMAIL=내이메일@example.com`을 추가하거나, `pnpm db:seed -- 내이메일@example.com`처럼 명령행 인자로 직접 넘겨도 된다. 자신의 실제 이메일로 시드해두면, 나중에 Supabase Auth(§3-4)를 연동했을 때 바로 그 계정으로 로그인 테스트를 할 수 있다.

### 3-9. `.npmrc`와 GitHub 패키지 인증 (참고, 보통 신경 쓸 필요 없음)

`.npmrc`에는 아래와 같이 `@ttoltori` 스코프 패키지를 GitHub 패키지 레지스트리에서 받아오도록 설정되어 있다.

```text
@ttoltori:registry=https://npm.pkg.github.com
//npm.pkg.github.com/:_authToken=${GITHUB_TOKEN}
```

이 프로젝트의 `packages/database`, `packages/api-client-core`, `packages/hono-api-kit`는 `workspace:*`로 로컬 복사본을 직접 참조하므로 **`GITHUB_TOKEN` 환경변수가 없어도 `pnpm install`이 정상 동작한다.** 이 설정은 나중에 이 공용 패키지들을 실제 GitHub 패키지 레지스트리에서 받아써야 하는 상황(예: 로컬 복사본 없이 순수 배포 버전만 쓰고 싶을 때)을 위한 것이다. 그런 경우가 아니라면 `GITHUB_TOKEN`을 설정하지 않아도 된다.

## 4. 자주 쓰는 명령

| 명령 | 설명 |
|---|---|
| `pnpm dev` | 개발 서버 실행 (프론트+API 통합, http://localhost:3001) |
| `pnpm build` | 프로덕션 빌드 생성 |
| `pnpm start` | 빌드된 결과물을 프로덕션 모드로 실행 |
| `pnpm lint` | ESLint 검사 |
| `pnpm typecheck` | TypeScript 타입 검사 (`tsc --noEmit`, 실제 파일을 만들지 않고 오류만 확인) |
| `pnpm test` | vitest로 단위 테스트 실행 |
| `pnpm db:migrate` | `database/migrations/myportal/*.sql`을 순서대로 적용 |
| `pnpm db:seed` | 개발용 사용자·기본 카테고리 생성 |
| `pnpm crawl:once` | 수집 시각이 된 소스를 한 번 수집 |
| `pnpm crawl:once --force` | 수집 시각 무시, 모든 구독 소스를 즉시 수집 |
| `pnpm crawl:watch` | 60초 간격으로 `crawl:once`를 반복 실행 |

src/

│  ├─ login/, auth/callback/  # 로그인 화면
│  ├─ page.tsx               # 메인 데스크 화면 (3분할 패널)
│  ├─ add-source/, sources/, sources/[id]/   # 소스 등록/관리 화면
│  ├─ categories/, schema-map/, keywords/, digest/  # 분류/스키마/키워드/다이제스트 설정 화면
│  └─ globals.css            # 프로토타입의 신문/전보 스타일 디자인 토큰
├─ components/
│  ├─ masthead.tsx           # 상단 헤더(마스트헤드) + 다크/라이트 테마 토글
│  └─ desk/                  # 메인 데스크 화면 컴포넌트, 리사이즈 가능한 패널 훅
├─ lib/
│  ├─ api.ts                 # 프론트엔드에서 쓰는 API 클라이언트 인스턴스

└─ server/                   # 백엔드 코드 (Next.js 없이도 단독 테스트 가능)
   ├─ app.ts                 # Hono 앱 조립: 미들웨어 연결, 라우터 등록, 인증 게이트
   ├─ routes/*.routes.ts     # 얇은 라우터 — 입력값 검증 후 features 함수 호출만 담당
   ├─ features/              # 실제 비즈니스 로직 + SQL이 여기 모여 있다
   │  ├─ auth/               # 매직링크 발급/확인, 세션 발급, requireAuth 미들웨어

   │  ├─ desk/ items/ sources/ categories/ tags/ subscriptions/

   │  └─ digest/             # 다이제스트 설정, 미리보기, 발송
   ├─ config/                # env.ts(환경변수 검증), db.ts(DB 커넥션 생성)
   ├─ scripts/               # migrate·seed·crawl-tick 실행 스크립트 + load-env.ts
   ├─ middleware/, utils/    # @ttoltori/hono-api-kit 재노출(re-export) — §5-1 참고
   └─ errors/                # 서비스 오류 코드(myportal 전용 ErrorCode) + AppError 서브클래스

요청이 처리되는 흐름을 한 줄로 요약하면:

```text
브라우저 → Next.js Route Handler(/api/[...path]) → Hono app → routes → features → .sql.ts → @ttoltori/database → Supabase PostgreSQL(myportal 스키마)
```

### 5-1. 공통 패키지 (`packages/`)

이 프로젝트만 쓰는 코드와, 여러 서비스가 함께 쓰는 코드를 구분해서 관리한다.

| 패키지 | 성격 | 역할 |
|---|---|---|
| `@myportal/api-contracts` | myportal 전용 | myportal API 요청/응답 형태를 정의한 zod 스키마, 오류 코드(`ErrorCode`) |
| `@myportal/myportal-api-client` | myportal 전용 | 프론트엔드가 API를 호출할 때 쓰는 함수 모음 |
| `@ttoltori/api-client-core` | 여러 서비스 공통 | `httpRequest`(HTTP 요청 공통 처리: 응답 envelope 파싱, 타임아웃, `ApiError`) |
| `@ttoltori/database` | 여러 서비스 공통 | `DatabaseClient`(SQL 실행/트랜잭션), PostgreSQL 커넥션 풀 |
| `@ttoltori/hono-api-kit` | 여러 서비스 공통 | request-id 부여 미들웨어, `AppError`, 표준 응답 형식(`success`/`error`/`paginated`), 오류 처리 연결(`attachErrorHandling`) |

`@ttoltori/*`로 시작하는 패키지들은 `myportal`뿐 아니라 다른 형제 프로젝트(`worldvs-web` 등)에서도 똑같이 필요한 "Hono 서버 보일러플레이트"라서 별도 저장소인 `shared-packages`에서 원본(canonical source)을 관리한다. 이 프로젝트의 `packages/database`, `packages/api-client-core`, `packages/hono-api-kit`는 그 원본의 **로컬 복사본**이다(`private: true`로 표시되어 npm에 배포되지 않고, `workspace:*`로 이 프로젝트 안에서만 참조된다). `@ttoltori/*` 코드를 고칠 일이 생기면 `shared-packages`의 원본을 먼저 고치고 이 프로젝트의 복사본에 동기화해야 한다.

`src/server/middleware/request-id.ts`와 `src/server/utils/response.ts`는 실제 구현이 없고 `@ttoltori/hono-api-kit`를 그대로 다시 내보내는(re-export) 파일이다 — 기존에 이 경로로 import하던 코드를 바꾸지 않아도 되게 하기 위한 하위 호환용 파일이다. `src/server/errors/error-codes.ts`의 `AppError`는 `@ttoltori/hono-api-kit`의 `AppError<TCode>`를 myportal의 `ErrorCode` 타입으로 좁힌 서브클래스일 뿐이다.

## 6. 데이터베이스

- 모든 테이블은 `myportal`이라는 전용 스키마(namespace) 안에 있다. 즉 SQL에서는 `myportal.users`, `myportal.items`처럼 스키마 이름을 붙여서 접근한다.
- 구조를 바꿔야 할 때는 `database/migrations/myportal/`에 **새 SQL 파일을 추가**한다. 이미 적용되어 배포된 마이그레이션 파일은 절대 수정하지 않는다(다른 환경에서 이미 실행됐기 때문에 내용을 바꾸면 환경 간 스키마가 어긋난다).
- 어떤 마이그레이션이 이미 적용됐는지는 `myportal.schema_migrations` 테이블이 기록한다.
- 핵심 테이블:
  - 계정: `users`, `sessions`, `magic_links`, `user_settings`
  - 분류: `categories`, `tags`, `subscriptions`, `subscription_tags`
  - 소스/수집 설정: `sources`, `source_fields`, `crawl_specs`
  - 수집된 데이터: `items`, `clusters`, `item_states`, `item_rule_matches`
  - 규칙: `keyword_rules`
  - 이력: `crawl_runs`, `crawl_jobs`, `digest_runs`, `manual_actions`

## 7. 수집 파이프라인

`src/server/features/crawl/` 안의 파일들이 하는 일:

1. `url.ts` — URL 정규화(불필요한 추적 파라미터 제거, 쿼리 정렬), SSRF(내부망 접근) 방어, `absolutize`(상대경로를 절대경로로), 중복 판정용 해시 생성.
2. `robots.ts` — 대상 사이트의 `robots.txt`를 읽고 캐시해서 수집 허용 여부(`robotsAllowed`)를 판단.
3. `fetcher.ts` — 타임아웃/응답 크기 제한이 있는 페이지 다운로드(`fetchPage`), 리다이렉트가 있을 때마다 SSRF 재검사.
4. `extract.ts` — RSS/Atom 파싱, 피드 자동 탐지, JSON-LD(ItemList) 파싱, DOM 구조를 보고 규칙을 추론하는 휴리스틱 명세 생성(`generateSpec`), 저장된 명세 적용(`applySpec`), 날짜 문자열 파싱.
5. `analyze.ts` — 사용자가 소스를 등록하기 전에 URL을 분석해서(단계별 로그 반환) 부모 목록 후보, robots 허용 여부, "링크만 수집" 여부 등을 판단.
6. `collector.ts` — 실제 수집 실행(`collectSource`): 다운로드 → 추출 → 중복 제거 → 키워드 매칭 → 클러스터링(비슷한 기사 묶기) → `crawl_runs`에 실행 기록 → 다음 수집 주기 자동 조정(새 글이 없으면 15분→최대 24시간까지 점점 늘림) → 연속 실패 시 명세 자동 재생성 시도. 소스를 처음 등록할 때 실행되는 `runBaseline`은 현재 시점 글들을 "기준선"으로 넣고 곧바로 읽음 처리해서, 목록에는 보이되 그 이후에 올라온 글만 "새 글"로 보이게 한다.
7. `cluster.ts` — 제목을 정규화한 키(`titleKey`)를 기준으로 여러 소스에 같은 내용이 올라왔을 때 하나로 묶는다.
8. `match.ts`(`features/keywords/`) — 등록된 키워드 규칙을 mute(숨김) > alert(강조 알림) > emphasize(단순 강조) 우선순위로 판정해서 `item_rule_matches`에 저장한다.

## 8. 인증 흐름

- `POST /v1/auth/magic-link` → 사용자가 이메일 입력 → `GET /v1/auth/confirm?token=...` → 토큰이 유효하면 `myportal_session`이라는 HttpOnly 쿠키를 발급(기본 30일 유지).
- 토큰은 원문이 아니라 SHA-256 해시로 데이터베이스에 저장하고, 1회용이며 만료 시간이 지나면 무효화된다.
- 세션 인증 검사는 `app.ts`에서 `/v1/*` 전체에 대해 딱 한 번만 걸어둔다. 예외는 `/v1/auth/*`(로그인 자체는 인증이 없어도 접근 가능해야 하니까)와 `/v1/internal/*`(사람의 로그인이 아니라 크론/스케줄러가 호출하므로 별도의 시크릿 키로 인증)이다.
- `/v1/internal/*`는 `x-internal-secret` 헤더 또는 `Authorization: Bearer` 헤더로 인증한다(§3-5).
- `src/middleware.ts`(Next.js 미들웨어)는 세션 쿠키가 있는지만 보고, 없으면 화면 접근 시 `/login`으로 돌려보낸다.

## 9. API 응답 규칙

성공 응답은 `{ success: true, data: {...}, meta: { requestId } }` 형태, 실패 응답은 `{ success: false, error: { code, message, details }, meta: { requestId } }` 형태로 통일되어 있다. 프론트엔드 코드는 사람이 읽는 오류 메시지가 아니라 `error.code` 값을 보고 분기 처리해야 한다(메시지는 나중에 자유롭게 바뀔 수 있지만 code는 안정적인 계약이기 때문). 서버 내부 SQL 문구, 스택 트레이스, 외부 서비스의 원본 오류 메시지는 절대 응답에 그대로 노출하지 않는다.

주요 엔드포인트: `/v1/auth/*`, `/v1/me`, `/v1/desk`, `/v1/items/*`, `/v1/categories/*`, `/v1/tags/*`, `/v1/subscriptions/*`, `/v1/sources/*`(analyze, create, collect, reanalyze, apply-spec), `/v1/keyword-rules/*`(preview), `/v1/digest/*`(settings, preview, send-now), `/v1/internal/*`(crawl-tick, digest-tick), `/health`.

## 11. 배포 (Vercel)

### 11-1. 프로젝트 Import

[vercel.com/new](https://vercel.com/new)에서 이 저장소를 Import한다.

**여러 앱이 감지된다.** pnpm 워크스페이스라 Vercel이 `packages/*`를 훑어서 `packages/hono-api-kit`을 Hono 앱으로, 루트를 Next.js 앱으로 각각 제시한다. `hono-api-kit`은 `private: true`인 **라이브러리**이고 서버 진입점이 없다(Vercel이 옆에 `Internal`이라고 표시해 준다). 배포할 것은 **`app` (Next.js) `/`** 하나다. 상단의 `Services`로 묶는 기능도 쓰지 않는다.

| 항목 | 값 |
|---|---|
| Framework Preset | Next.js (자동 감지) |
| **Root Directory** | **기본값 그대로 비워둔다** |
| Install / Build Command | 건드리지 않는다 — `vercel.json`이 지정한다 |

Root Directory에 `myportal`을 넣으면 안 된다. **이 저장소의 루트가 이미 `myportal`이다**(`git rev-parse --show-toplevel`로 확인할 수 있다). Import 화면에서 Next.js 앱의 경로가 `/`로 표시되는 것이 그 증거다.

### 11-2. 환경변수 — Deploy를 누르기 전에 넣는다

Settings → Environment Variables. §3의 설명과 같은 값이다.

**필수**

| 변수 | 값 |
|---|---|
| `DATABASE_URL` | 운영 Supabase 연결 문자열 (Session pooler, 6543 권장) |
| `APP_BASE_URL` | 배포 도메인 (예: `https://myportal.vercel.app`) |
| `INTERNAL_API_SECRET` | 운영용으로 새로 발급 (로컬 값 재사용 금지) |
| `AUTH_DEV_MODE` | **`false`** (§3-3의 보안 경고) |
| `ALLOWED_EMAILS` | 로그인을 허용할 이메일. **비우면 누구나 로그인된다** |

**선택**

| 변수 | 비우면 |
|---|---|
| `LLM_API_KEY` | LLM 필드 추론이 꺼지고 제목·링크만 추출한다 (§3-6) |
| `LLM_API_BASE` / `LLM_MODEL` / `LLM_DAILY_LIMIT` / `LLM_DAILY_LIMIT_SYSTEM` | 기본값 적용 — 보통 넣지 않는다 |
| `SUPABASE_URL` / `SUPABASE_SERVICE_ROLE_KEY` | 로그인 링크가 메일로 가지 않는다 (11-3 참고) |
| `SMTP_URL` / `MAIL_FROM` | 다이제스트가 발송되지 않고 `queued`로만 기록된다 |
| `CHROMIUM_PATH` | **비워야 한다.** 서버리스에서 `@sparticuz/chromium`이 자동으로 쓰인다 |

**`NEXT_PUBLIC_API_URL`은 설정하지 않는다.** 프론트와 API가 같은 출처이므로 `src/lib/api.ts`가 브라우저의 현재 도메인에서 `{origin}/api`를 유도한다. 도메인을 바꾸거나 preview 배포에 접속해도 자동으로 맞고, Vercel이 `NEXT_PUBLIC_` 접두사에 대해 띄우는 경고(공개 접두사는 값을 브라우저에 노출한다)를 상대할 일도 없다.

굳이 넣는다면 프론트와 API를 **다른 도메인**에 두는 구성일 때뿐이다. 그때는 `NEXT_PUBLIC_*`이 **빌드 시점에 번들에 박힌다**는 점에 주의한다 — 값을 나중에 고쳐도 **재배포(빌드 캐시 끄고)** 전까지 반영되지 않는다. 빈 문자열로 두면 미설정과 같게 처리된다.

### 11-3. 로그인 경로를 먼저 정한다

`AUTH_DEV_MODE=false`에서 매직링크 발송 경로는 `src/server/features/auth/auth.ts`가 이렇게 정한다.

- `SUPABASE_URL`·`SUPABASE_SERVICE_ROLE_KEY`가 있으면 → Supabase Auth가 메일을 보낸다.
- 없으면 → 링크가 **Vercel 함수 로그에만** 출력된다. 로그인할 때마다 로그를 뒤져야 한다.

**`SMTP_URL`은 매직링크에 쓰이지 않는다.** 다이제스트 메일 전용이다.

제대로 쓰려면 Supabase 환경변수를 넣고, Supabase 대시보드의 **Authentication → URL Configuration**에 배포 도메인을 Redirect URL로 등록한다. 첫 로그인만 함수 로그로 해결하고 나중에 붙여도 된다.

`AUTH_DEV_MODE=true`로 배포하는 선택지는 없다. 로그인 링크가 API 응답에 그대로 실려 **누구나 아무 계정으로 로그인**할 수 있다.

### 11-4. 마이그레이션

Vercel은 마이그레이션을 실행해주지 않는다. 로컬 터미널에서 운영 `DATABASE_URL`을 가리킨 상태로 직접 실행한다.

```bash
pnpm db:migrate
```

로컬 `.env.local`이 이미 운영 DB를 가리키고 있다면 그대로 실행하면 된다. 개발/운영 DB를 분리했다면 `DATABASE_URL`을 임시로 바꿔서 실행한다. `schema_migrations`가 적용 여부를 기록하므로 재실행은 안전하다.

### 11-5. Cron

`vercel.json`에 정의되어 있고, 현재는 수집만 **하루 1회** 돈다.

```json
"crons": [{ "path": "/api/v1/internal/crawl-tick", "schedule": "0 21 * * *" }]
```

- **스케줄은 UTC 기준이다.** `0 21 * * *`은 06:00 KST다.
- Vercel Cron은 GET + `Authorization: Bearer`로 호출한다. 내부 인증이 두 방식을 모두 지원하므로 별도 설정이 필요 없다.
- 다이제스트를 쓰게 되면 `/api/v1/internal/digest-tick`을 이 배열에 추가한다.

**요금제별 cron 개수·빈도 제한을 확인한다.** Hobby 플랜은 제한이 빡빡해서 분 단위 스케줄이 거부되거나 하루 1회로 내려갈 수 있다. 최신 수치는 Vercel 문서를 봐야 한다.

**하루 1회로 돌 때의 제약**: `crawl-tick`은 한 번에 최대 `TICK_BATCH`(20)개 소스만 처리한다(`src/server/routes/internal.routes.ts`). 쿼리가 `order by next_crawl_at asc nulls first`라 오래 묵은 것부터 돌아가며 잡으므로 영구히 누락되는 소스는 없지만, **소스가 20개를 넘으면 실질 수집 주기가 늘어난다**(40개면 이틀에 한 번). 적응형 주기(신규가 있으면 15분으로 단축)도 하루 1회가 상한이라 사실상 무의미해진다.

소스가 많아지면 요건정의서 NFR-O4가 정한 대안으로 옮긴다 — GitHub Actions `schedule`이 `x-internal-secret` 헤더와 함께 `/api/v1/internal/crawl-tick`을 호출하는 방식이다. 무료이고 빈도 제한이 느슨하다.

### 11-6. 함수 실행 시간

`crawl-tick`은 소스를 최대 20개 처리하고, JS 렌더링이 필요한 소스는 헤드리스 Chromium을 띄운다. `fetchPage` 타임아웃만 15초다. `vercel.json`에 `maxDuration` 설정이 없어 플랜 기본값을 따른다.

배포 후 `crawl_runs`에 타임아웃 오류가 쌓이면 `src/app/api/[...path]/route.ts`에 추가한다(플랜 상한 안에서만 올라간다).

```ts
export const maxDuration = 60;
```

### 11-7. 배포 후 확인

1. `/login`에서 이메일 입력 → 메일 또는 함수 로그로 링크를 받아 로그인
2. `/add-source`에서 목록 URL 분석 → 분석 단계에 `AI 필드 분석`이 `ok`로 뜨는지 (LLM 키가 먹었는지 여기서 바로 보인다)
3. 미리보기 필드 라벨이 한글인지, 헤더에 `· AI 추론` 배지가 붙는지
4. 소스 상세에서 `다시 분석` → 힌트 입력칸에 저장된 힌트가 채워져 보이는지
5. 다음 날 06:00 KST 이후 `crawl_runs`에 cron 실행 기록이 쌓이는지

LLM 호출·비용은 이렇게 본다.

```sql
select purpose, count(*), sum(prompt_tokens), sum(completion_tokens)
from myportal.llm_calls
where created_at >= current_date
group by purpose;
```

## 12. 문제가 생겼을 때 (트러블슈팅)

- **`DATABASE_URL is not set` 오류로 서버가 안 뜬다** → `.env.local` 파일이 실제로 있는지, `DATABASE_URL` 값이 채워져 있는지 확인. `cp .env.example .env.local`을 빼먹었을 가능성이 높다.
- **`pnpm crawl:once`이 `no due sources`만 출력한다** → 오류가 아니다. 소스는 `next_crawl_at` 시각이 되어야 수집된다(신규 항목이 없으면 주기가 2배씩 늘어남). 출력에 "다음 예정 시각"이 표시된다. 즉시 수집하려면 `pnpm crawl:once --force`를 사용한다.
- **`pnpm crawl:once` 실행 시에도 같은 오류가 난다** → CLI 스크립트는 `src/server/scripts/load-env.ts`를 통해 `.env.local`을 읽는다. 이 스크립트를 프로젝트 루트가 아닌 다른 폴더에서 실행하면 `.env.local`을 못 찾을 수 있으니 `myportal` 폴더 루트에서 실행해야 한다.
- **로그인 링크를 눌러도 로그인이 안 된다** → `AUTH_DEV_MODE=true`인지 확인. 링크는 30분 안에만 유효하고 1회용이라, 같은 링크를 다시 누르면 실패하는 게 정상이다(새로 요청하면 된다).
- **`/api/v1/internal/*` 호출 시 401(UNAUTHORIZED)** → `x-internal-secret` 헤더 값이 `.env.local`의 `INTERNAL_API_SECRET`과 정확히 일치하는지 확인.
- **포트 3001이 이미 사용 중이라고 나온다** → 이전에 띄운 `pnpm dev`가 아직 실행 중일 수 있다. 해당 터미널을 찾아 종료하거나 `netstat`/작업 관리자로 3001 포트를 쓰는 프로세스를 종료한다.
- **Supabase 콘솔에서는 테이블이 보이는데 화면에는 데이터가 안 보인다** → 로그인한 사용자와 데이터가 속한 사용자가 다를 수 있다. myportal은 사용자별로 데이터가 분리되어 있으므로(각 `items`, `sources` 등이 `user_id`로 구분됨), 시딩한 계정(`dev@myportal.local`)으로 로그인했는지 확인한다.
- **`x-request-id` 응답 헤더 / `meta.requestId`** — 모든 API 응답에 요청 고유 ID가 붙는다. 서버 콘솔 로그에서 문제가 된 요청을 추적할 때 이 값으로 검색하면 빠르다.
- **소스 수집 결과가 계속 비어있다** → 소스 상세 화면의 "수집 실행 로그"에서 `crawl_runs.error_code`를 확인하고, `/sources/[id]`에서 **"다시 분석"**을 실행한다. 패널에서 추출 미리보기를 확인하고 필요하면 '목록 항목 힌트'를 고쳐 다시 돌린 뒤 '적용'하면 새 명세가 저장되고 기존 항목에 새 필드가 백필된다. 사이트 개편으로 명세가 깨진 경우가 대부분이다.
- **`.vscode/launch.json`**: VSCode/Windsurf에서 `dev` 서버, `crawl:once`, `db:migrate`, 특정 테스트 파일 실행을 디버거로 바로 실행할 수 있는 설정이 이미 준비되어 있다. 왼쪽 "실행 및 디버그" 패널에서 선택해서 사용하면 된다.
