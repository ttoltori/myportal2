# myportal 개발자 가이드

`myportal`은 URL을 등록하면 새 글·공고를 주기적으로 수집해 한눈에 보여주는 개인 모니터링 포털이다. 프론트엔드와 Hono 백엔드가 하나의 Next.js 앱(`myportal-web`, port 3001)에 통합되어 있다.

## 1. 로컬 개발 시작하기

### 요구 사항

- Node.js 20 이상 (22 권장 — `process.loadEnvFile` 사용)
- pnpm
- PostgreSQL 16 (로컬 Docker 또는 Supabase)

### 설정 순서

```bash
# 1) 의존성 설치
pnpm install

# 2) 환경변수 — .env.example을 복사해 .env.local 작성
cp .env.example .env.local

# 최소 필수값
DATABASE_URL=postgres://postgres:myportal@localhost:5432/myportal
INTERNAL_API_SECRET=임의의-긴-문자열
AUTH_DEV_MODE=true          # 로컬에서는 매직링크가 이메일 대신 응답으로 반환됨

# 3) PostgreSQL 기동 (Docker 예시)
docker run -d --name myportal-pg \
  -e POSTGRES_PASSWORD=myportal -e POSTGRES_DB=myportal \
  -p 5432:5432 postgres:16-alpine

# 4) 스키마 생성 + 개발 사용자 생성
pnpm db:migrate
pnpm db:seed                # dev@myportal.local 사용자 생성

# 5) 개발 서버
pnpm dev                    # http://localhost:3001
```

### 로그인

`AUTH_DEV_MODE=true`이면 `/login`에서 이메일을 입력했을 때 실제 메일 대신 API 응답(및 서버 로그)으로 로그인 링크가 출력된다. 화면의 개발용 링크를 누르면 세션 쿠키가 발급된다.

### 수집 워커

주기 수집은 두 가지 방법으로 돌릴 수 있다.

```bash
# 방법 A: 로컬 워커 스크립트
pnpm crawl:once             # due 소스 1회 수집
pnpm crawl:watch            # 60초 간격 반복

# 방법 B: HTTP 엔드포인트 (운영 cron과 동일 경로)
curl -X POST http://localhost:3001/api/v1/internal/crawl-tick \
  -H "x-internal-secret: $INTERNAL_API_SECRET"
curl -X POST http://localhost:3001/api/v1/internal/digest-tick \
  -H "x-internal-secret: $INTERNAL_API_SECRET"
```

## 2. 자주 쓰는 명령

| 명령 | 설명 |
|---|---|
| `pnpm dev` | Next.js 개발 서버 (3001) |
| `pnpm build` | 프로덕션 빌드 |
| `pnpm typecheck` | `tsc --noEmit` |
| `pnpm test` | vitest |
| `pnpm db:migrate` | `database/migrations/myportal/*.sql` 순서 적용 |
| `pnpm db:seed` | 개발 사용자 + 미분류 카테고리 생성 |
| `pnpm crawl:once` / `crawl:watch` | 수집 워커 |

## 3. 환경변수 요약

| 변수 | 필수 | 설명 |
|---|---|---|
| `DATABASE_URL` | ✓ | PostgreSQL 접속 문자열. `myportal` 스키마는 마이그레이션이 만든다 |
| `APP_BASE_URL` | | 매직링크 콜백 기준 URL (기본 `http://localhost:3001`) |
| `NEXT_PUBLIC_API_URL` | | 프론트엔드 API base (기본 `/api` 대신 절대 URL 지정 가능) |
| `ALLOWED_EMAILS` | | 쉼표 구분 허용 이메일. 비우면 전체 허용 |
| `AUTH_DEV_MODE` | | true면 매직링크를 API 응답으로 반환 (로컬 전용) |
| `SESSION_TTL_DAYS` | | 세션 유효 일수 (기본 30) |
| `INTERNAL_API_SECRET` | cron 시 ✓ | `/v1/internal/*` 보호용 공유 시크릿 |
| `SUPABASE_URL` / `SUPABASE_SERVICE_ROLE_KEY` | | 설정하면 Supabase Auth 매직링크 사용 |
| `SMTP_URL`, `MAIL_FROM` | | 설정하면 다이제스트 실발송. 없으면 `queued`로만 기록 |
| `LLM_API_BASE/KEY/MODEL` | | 설정하면 추출 명세 자동 생성에 OpenAI 호환 API 사용. 없으면 휴리스틱만 |
| `CRAWL_USER_AGENT` | | 수집 UA. 기본 `myportal-bot/0.1 (+APP_BASE_URL)` |

`.npmrc`의 `@ttoltori` 레지스트리 인증은 사용자 레벨 `~/.npmrc`에 `GITHUB_TOKEN`을 넣어야 한다(프로젝트 `.npmrc`에서는 환경변수가 확장되지 않는다). 로컬 복사본 패키지를 쓰므로 토큰 없이도 설치된다.

## 4. 코드 구조

```text
src/
├─ app/                     # Next.js App Router (화면)
│  ├─ api/[...path]/route.ts  # Hono 어댑터 — /api/* → Hono /v1/*로 전달만 함
│  ├─ login/, auth/callback/  # 인증 화면
│  ├─ page.tsx               # 데스크(3패널)
│  ├─ add-source/, sources/, sources/[id]/
│  ├─ categories/, schema-map/, keywords/, digest/
│  └─ globals.css            # 프로토타입 토큰(신문/전보 디자인) 이식
├─ components/
│  ├─ masthead.tsx           # 상단 마스트헤드 + 테마 토글
│  └─ desk/                  # desk-client.tsx, use-resizable.ts
├─ lib/
│  ├─ api.ts                 # createMyportalClient 인스턴스
│  └─ shell.ts               # 토스트, 실행취소 띠, 시간 포맷
└─ server/                   # 백엔드 — Next.js 없이도 테스트 가능
   ├─ app.ts                 # Hono 앱 조립 + 세션 인증 게이트
   ├─ routes/*.routes.ts     # 얇은 라우터 (검증 + 핸들러 호출)
   ├─ features/              # 비즈니스 로직 + .sql.ts (SQL 분리)
   │  ├─ auth/               # 매직링크, 세션, requireAuth
   │  ├─ crawl/              # url(SSRF)·fetcher·robots·extract·analyze·collector·cluster
   │  ├─ desk/ items/ sources/ categories/ tags/ subscriptions/
   │  ├─ keywords/           # 규칙 CRUD + 매칭 + 미리보기
   │  └─ digest/             # 설정, 미리보기, 발송
   ├─ config/                # env.ts(환경 검증), db.ts(커넥션)
   ├─ scripts/               # migrate·seed·crawl-tick + load-env.ts
   └─ errors/                # AppError + 표준 오류 코드
```

요청 흐름: `Next.js Route Handler → Hono app → routes → features → .sql.ts → @ttoltori/database → PostgreSQL(myportal 스키마)`.

## 5. 데이터베이스

- 스키마: `myportal` (테이블에 서비스 prefix 반복 금지)
- 모든 구조 변경은 `database/migrations/myportal/`에 새 SQL 파일로 추가한다. **적용된 파일은 수정하지 않는다.**
- 적용 이력은 `myportal.schema_migrations`가 관리한다.
- 핵심 테이블: `users·sessions·magic_links·user_settings`(계정), `categories·tags·subscriptions·subscription_tags`(분류), `sources·source_fields·crawl_specs`(소스/명세), `items·clusters·item_states·item_rule_matches`(수집물), `keyword_rules`(규칙), `crawl_runs·crawl_jobs`(수집 이력/큐), `digest_runs·manual_actions`(이력).

## 6. 수집 파이프라인

`src/server/features/crawl/`:

1. `url.ts` — URL 정규화(트래킹 파라미터 제거, 쿼리 정렬), SSRF 방어(사설 IP/로컬 호스트 차단), `absolutize`, 중복해시.
2. `robots.ts` — robots.txt 파싱·캐시, `robotsAllowed`.
3. `fetcher.ts` — 타임아웃/크기 제한/리다이렉트 재검사가 있는 `fetchPage`.
4. `extract.ts` — RSS/Atom 파싱, 피드 자동탐지, JSON-LD ItemList, DOM 휴리스틱 스펙 생성(`generateSpec`), 스펙 적용(`applySpec`), 날짜 파싱.
5. `analyze.ts` — 소스 등록 전 분석(로그 단계 반환, 부모 목록 후보, robots/link-only 판정).
6. `collector.ts` — `collectSource`: 가져오기→추출→중복 제거→키워드 매칭→클러스터링→`crawl_runs` 기록→주기 자동조정(무소식 시 지수 백오프 15분→24시간)→연속 실패 시 명세 자동 재생성 시도. `runBaseline`은 신규 등록 시 과거 항목을 `is_baseline=true`로 적재해 '읽음' 처리한다.
7. `cluster.ts` — 제목 키(`titleKey`) 기반 유사 기사 묶기.
8. `match.ts` (keywords/) — mute > alert > emphasize 우선순위로 규칙 매치를 `item_rule_matches`에 저장.

## 7. 인증

- `POST /v1/auth/magic-link` → `GET /v1/auth/confirm?token=` → `myportal_session` HttpOnly 쿠키 발급(30일).
- 토큰은 SHA-256 해시로 저장, 1회용, 만료시간 검사.
- 세션 인증은 `app.ts`의 `/v1/*` 게이트에서 한 번만 한다. `/v1/auth/`, `/v1/internal/`는 면제.
- `/v1/internal/*`는 `x-internal-secret` 또는 `Authorization: Bearer`(Vercel cron용) 헤더로 인증.
- `src/middleware.ts`(Next)가 세션 쿠키 존재 여부로 페이지를 보호해 로그인 화면으로 보낸다.

## 8. API 규칙

성공 `{ success, data, meta.requestId }`, 실패 `{ success:false, error:{code,message,details}, meta }`. 클라이언트는 메시지가 아니라 `code`로 분기한다. 내부 SQL·스택·프로바이더 원문 오류는 응답에 넣지 않는다.

주요 엔드포인트: `/v1/auth/*`, `/v1/me`, `/v1/desk`, `/v1/items/*`, `/v1/categories/*`, `/v1/tags/*`, `/v1/subscriptions/*`, `/v1/sources/*`(analyze, create, collect, rebuild-spec), `/v1/keyword-rules/*`(preview), `/v1/digest/*`(settings, preview, send-now), `/v1/internal/*`(crawl-tick, digest-tick), `/health`.

## 9. 테스트

```bash
pnpm test          # vitest run
```

핵심 규칙만 테스트한다(§20): `crawl/url.test.ts`(정규화·SSRF·해시), `crawl/extract.test.ts`(피드/JSON-LD/스펙 적용/날짜), `keywords/match.test.ts`(키워드·제외어 매칭). DB 필요 경로는 라우트 수준에서 얇게 유지하고 로직을 순수 함수로 분리해 단위 테스트한다.

## 10. 배포 (Vercel)

1. 프로젝트 루트를 이 디렉터리로 지정하고 `pnpm install`/`pnpm build`를 그대로 사용한다(`vercel.json`에 설정됨).
2. 환경변수: `DATABASE_URL`(Supabase pooled 권장), `APP_BASE_URL`(프로덕션 도메인), `INTERNAL_API_SECRET`, 필요 시 `SUPABASE_*`, `SMTP_URL`, `MAIL_FROM`, `ALLOWED_EMAILS`. `AUTH_DEV_MODE`는 반드시 `false`.
3. 크론: `vercel.json`이 `/api/v1/internal/crawl-tick`(30분)과 `/digest-tick`(10분)을 호출한다. Vercel cron은 GET + `Authorization: Bearer`로 호출하므로 `INTERNAL_API_SECRET`을 Bearer로 전달되게 환경변수에 설정한다.
4. 마이그레이션은 배포 전/후에 로컬에서 `DATABASE_URL`을 운영 DB로 지정해 `pnpm db:migrate`를 실행한다.

## 11. 디버깅 팁

- `x-request-id` 응답 헤더와 `meta.requestId`로 서버 로그의 요청을 추적한다.
- 수집 실패 원인은 `myportal.crawl_runs`의 `error_code`, 소스 상세 화면의 "수집 실행 로그"에서 본다.
- 소스가 계속 빈 결과를 내면 `rebuild-spec`으로 명세를 재생성하거나 `/add-source`에서 다시 분석한다.
- `.vscode/launch.json`에 dev 서버, crawl-tick, migrate, vitest 구성이 있다.
